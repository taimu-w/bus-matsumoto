# 経路検索機能 改善仕様書

作成日: 2026-08-11

## 0. この仕様書の位置づけ

現行の経路検索（`services/routeSearch.js` + `frontend/app.js` 内のルート検索UI）を全面的に作り直すための仕様書。
実装はこの仕様書に基づいて行う。対象となる要望は次の6点。

| # | 要望 | 対応する章 |
|---|---|---|
| 1 | 路線カラーが使われていない。路線カラーに基づいたデザインにする | 6章 |
| 2 | バス停検索画面のように、ひらがな・ローマ字でも検索できるようにする | 3章 |
| 3 | バス停をタップすると `/busstop` へ移動できる／乗るバスの通過バス停・時刻がわかる | 5.4章・6.4章 |
| 4 | GTFSの運賃データを取得して運賃を表示する | 4章 |
| 5 | カレンダーで日付を選択して検索できるようにする | 5.1章・6.2章 |
| 6 | 経路がたまに見つからないのをできるだけ防ぐ | 2章・7章 |

## 1. 現行実装の問題点（なぜ作り直すのか）

現行の `routeSearch.js` はDBの `stops` / `daily_trips` / `daily_trip_stop_times` を検索対象にしている。
この構造そのものが、上記6要望のうち5つを実現できない原因になっている。

| 現行の作り | それが引き起こす問題 |
|---|---|
| DBの `daily_trips`（当日ぶんしか生成されない）を見る | **日付を選んで検索できない**（要望5）。当日の便が未生成・生成失敗のときは検索結果がゼロになる |
| DBの `stops` は路線×方向×順序で正規化され、GTFSの `stop_id`・`zone_id`・標柱を持たない | **運賃を引けない**（要望4）。**`/busstop` のstopKeyへ変換できない**（要望3）。`name_kana` は持つがローマ字は無い（要望2） |
| 停留所の一致判定が「バス停名の完全一致」 | 表記ゆれ・別停留所名（例:「松本駅前」と「松本駅お城口」）でつながらず、**経路が見つからない**（要望6） |
| 直通は「出発地と目的地の両方の名前を持つ路線」に限定 | 路線をまたぐ経路が直通候補に出ない |
| 乗換は**直通が0件のときだけ**・**1回まで**・乗換地点は**同名バス停のみ**・各区間は**最速1本だけ**採用 | 乗換2回が必要な区間、徒歩数十mの別名バス停での乗換が**まったく出ない**（要望6の主因） |
| 路線カラー（`routes.color`）を結果に載せていない | **路線カラーが使えない**（要望1） |
| 便の全通過停留所を返していない | **通過バス停・通過時刻を表示できない**（要望3） |

一方、時刻表検索機能（`services/gtfsTimetable.js`）は既にGTFSファイルを直接インメモリインデックス化しており、
**任意日付のダイヤ判定・ひらがな/ローマ字検索・路線カラー・stop_id・標柱・便ごとの全通過時刻**をすべて持っている。
バス停検索機能（`/busstop`）のstopKeyもこのインデックスのものである。

→ **経路検索の探索基盤を、DBからGTFSインメモリインデックス（`gtfsTimetable.js`）へ移す。**
リアルタイム情報（遅延・予測時刻・車両位置）は、バス停検索機能が既に使っている
`realtimeTripLookup.js` の橋渡し（GTFS識別子 → 当日の `daily_trips`）で**上から重ねる**。
これはバス停検索機能の「接近中のバス」（`busStopApproaching.js`）と同じ設計であり、新しい依存関係を増やさない。

## 3. バス停の指定（要望2）

### 3.1 候補検索

`GET /api/route-search/stops?q={文字列}&limit={n}`

- `gtfsTimetable.searchStops()` をそのまま使う。すなわち**漢字・ひらがな・カタカナ・ローマ字（大文字小文字・全半角不問）**に対応し、前方一致を優先して部分一致も返す。時刻表検索・バス停検索と**まったく同じ検索体験**にする。
- 返す `stopKey` は**GTFSインデックスのグループキー**（`/busstop/{stopKey}` や `/timetable/stops/{stopKey}` と同じ値）。
  - これにより、経路検索の結果から `/busstop` へ**IDのまま**遷移できる（要望3）。現行のような名前による橋渡し（`navigateToBusStopByName`）は不要になる。
- レスポンス（`stops[]`）:

```jsonc
{
  "stopKey": "100",
  "name": "松本バスターミナル",
  "kana": "まつもとばすたーみなる",      // nameHiragana
  "romaji": "Matsumotobasutaminaru",
  "platformCount": 6,
  "lat": 36.2302, "lon": 137.9667,
  "routes": [ { "routeId": "11", "feedId": "guruttomatsumotobus1",
                "name": "横田信大循環線", "shortName": "", "color": "FF9900", "textColor": "FFFFFF" } ]
}
```

### 3.2 自由文字列（候補未選択）での検索

候補を選ばずに検索した場合は、同じ `searchStops()` で先頭最大3件のバス停を候補とみなし、
**その全組み合わせ**を探索してもっとも良い経路を返す。あいまい一致で検索したことは結果画面に明示する。

### 3.3 バス停の同一視

GTFSインデックスの統合ルール（`gtfsTimetable.js` の `buildGroups()`：同一ベースID＋同名／同名かつ400m以内は1件へ統合）をそのまま使う。
複数フィードに同じ物理バス停が別IDで入っているケースはこの時点で吸収済みであり、
**「アルピコのバスで着いて松本市営のバスに乗り継ぐ」ような経路が同一バス停の乗換として自然に見つかる。**

## 4. 運賃（要望4）

### 4.1 データの取得

GTFS ZIPには `fare_attributes.txt` / `fare_rules.txt` が含まれている（両フィードとも実在を確認済み）が、
現行の `gtfsFeedManager.js` は `MANAGED_GTFS_FILES` に無いファイルを展開先へ配置しないため、ディスク上に存在しない。

- `OPTIONAL_GTFS_FILES` に `fare_attributes.txt` と `fare_rules.txt` を追加する。
- **`REQUIRED_GTFS_FILES` には絶対に追加しない。** 持たないフィードが1つでもあると全フィードのGTFS更新が止まる（CLAUDE.md 既知の注意点）。
- 読み込みは `readCsvIfExists()` を使い、無ければ「運賃不明」として機能全体は成立させる。

### 4.2 運賃インデックス（`gtfsFare.js`）

フィードごとに以下を構築し、`gtfsTimetable` のインデックスと同じTTL・無効化タイミングで作り直す。

- `fareById`: `fare_id` → `{ price, currency, paymentMethod, transfers }`
- `rulesByRoute`: `route_id`（空文字＝全路線）→ ルール配列 `{ fareId, originId, destinationId, containsId }`
- `zoneByStopId`: `stop_id` → `zone_id`（`stops.txt` の `zone_id`。松本のデータでは `zone_id = stop_id`）

### 4.3 運賃の決定ルール

`lookupFare(feedId, routeId, boardStopId, alightStopId)`

1. 乗車・降車の `stop_id` から `zone_id` を求める。
2. 対象ルールを「その路線のルール」＋「route_id が空のルール（全路線共通）」とする。
3. 各ルールについて、`origin_id`／`destination_id` が空 or 一致していれば適用可能とする（GTFS仕様どおり）。
4. 適用可能なルールが複数ある場合は**より限定的なもの**を優先する。優先度は
   `origin+destination 指定 > どちらか一方だけ指定 > 両方とも空`、同順位なら**運賃の安い方**を採用する。
5. 1件も該当しない場合は `null`（＝運賃不明）を返す。**推測はしない。**

`contains_id` は今回のデータに存在しないため未対応とする（存在しても無視して他の条件だけで判定する）。

### 4.4 表示仕様

- 区間（leg）ごとに運賃を表示し、経路全体の合計も表示する。
- 乗換がある場合は単純合計とする（`fare_attributes.transfers = 0`＝乗継割引なし、というデータどおりの扱い）。
- 1区間でも運賃不明があれば、合計に「一部不明」を明示する（合計を出さないのではなく、判明ぶんの合計＋注記）。
- 画面に「運賃はGTFSデータに基づく目安です。実際の運賃は事業者にご確認ください。」と常時注記する。

## 5. 経路探索エンジン（`gtfsRouteSearch.js`）

### 5.1 入力

| パラメータ | 内容 | 既定値 |
|---|---|---|
| `fromStopKey` / `from` | 出発地（stopKey または自由文字列） | 必須 |
| `toStopKey` / `to` | 目的地（stopKey または自由文字列） | 必須 |
| `date` | 検索する日付（`YYYY-MM-DD`）＝**カレンダーで選択した日**（要望5） | 本日（JST） |
| `time` | 出発時刻（`HH:MM`。この時刻以降に出発する経路を探す） | 現在時刻（本日のとき）／`05:00`（他日のとき） |
| `limit` | 返す経路数 | 5 |

到着時刻を指定しての逆引き検索（「◯時までに着きたい」）は今回の要望に含まれないため対象外とする。
実装する場合は探索を時間反転させる必要があり、エンジンの構造そのものに手を入れることになる。

### 5.2 運行日の扱い

`gtfsTimetable.getActiveServices(index, dateStr)`（`calendar.txt` の有効期間＋曜日、`calendar_dates.txt` の例外を反映）で
その日に有効な `service_id` を求め、その `service_id` を持つ便だけを探索対象にする。

**日跨ぎの扱い**（見つからない経路を減らすため、要望6）:

- 前日サービスの24時超え便（例: 前日の `24:30` 発）を **−86400秒シフト**して当日の `0:30` として取り込む。
  → 深夜0時台の検索で「昨日のダイヤの深夜便」が正しく出る。
- 翌日サービスの便を **+86400秒シフト**して取り込む。
  → 終バス後に検索したとき、翌朝の始発が「翌日 5:40」として出る（同日の候補があればそちらが必ず先に選ばれる）。
- 表示上、`86400`秒以上の時刻は `翌日 5:40` のように日付を添える。

### 5.3 探索アルゴリズム

RAPTOR（ラウンド型）方式を採用する。ダイクストラではなくRAPTORにするのは、
**「乗換回数ごとの最良解（パレート最適解）」が1回の実行で同時に得られる**ため、
「直通は遅いが乗換1回なら早い」といった複数案を自然に列挙できるからである。

```
τ[k][stop] : k回乗車したあとに stop へ到着できる最早時刻
ラウンド0 : τ[0][出発地] = 基準時刻。徒歩接続で近傍バス停へ展開。
ラウンドk : 直前ラウンドで更新されたバス停から乗車できる便を走査し、
            その便の以降のバス停の到着時刻を更新する。
            更新されたバス停から徒歩接続を relax する。
```

- **乗車可能条件**: `pickup_type != 1` かつ 便の発車時刻 ≥ そのバス停への到着時刻 ＋ 乗換余裕（同一バス停 60秒、徒歩接続は徒歩所要時間）。ラウンド1（最初の乗車）では乗換余裕を課さない。
- **降車可能条件**: `drop_off_type != 1`。
- **徒歩接続（footpath）**: バス停グループ間の直線距離が `WALK_RADIUS_METERS`（既定400m、フォールバック時800m）以内なら徒歩で乗換できるものとし、徒歩時間 = 距離 ÷ 80m/分（最低60秒）。緯度経度のグリッドで近傍だけを比較し、半径ごとに1度だけ作ってキャッシュする。
  - **これが「経路が見つからない」の最大の対策**である。現行は同名バス停でしか乗り換えられない。
  - **徒歩の連鎖（徒歩→徒歩）は禁止する。** 同一ラウンド内で既に徒歩ラベルが付いたバス停からは再relaxしない。許すと「4分歩いて5分歩いて…」という非現実的な経路が最速解になる。
  - 1経路あたりの徒歩の合計が `MAX_TOTAL_WALK_MINUTES`（25分）を超える案は、他に候補があるなら出さない。
- **枝刈り**: 目的地への現在の最良到着時刻を超える更新は捨てる。基準時刻＋探索窓（既定6時間）より後に出発する便は見ない。
- **最大ラウンド数**: 3（＝乗換2回まで）。フォールバック時は4（乗換3回まで）。
- **frequencies.txt** 由来の便は、`gtfsTimetable` と同じく仮想便へ展開してから探索対象に入れる（現行フィードには存在しないが、将来フィードが変わっても壊れないようにする）。

### 5.4 複数候補の作り方

1. 1回の探索で、ラウンドごと（乗換0回／1回／2回）の最良経路をすべて取り出す。
2. 先頭区間の発車時刻を1分進めて再探索し、これを `limit` 件そろうまで最大12回繰り返す（＝「次の便」「その次の便」が並ぶ）。
3. **徒歩接続を使わない探索も必ず実行し、結果に混ぜる。** 徒歩を許すと「1駅手前で降りて歩く」方が最速になり、バスだけで完結する案が枝刈りで消えてしまう。利用者はふつう歩かない案も知りたいので、両方を候補に残す。
4. 同一の便構成（全区間の `tripId` と乗降バス停が同じ）は重複として除外する。
5. 並び順は**到着時刻の早い順**、同着なら乗換回数の少ない順。
6. `isRecommended`（おすすめ）は `到着時刻 + 乗換回数×5分 + 徒歩時間×0.5` が最小の1件に付ける。
   単純な最速ではなく「乗換が少なく歩かない経路」を適度に優遇するため。

### 5.6 リアルタイムの重ね合わせ

- 検索日が**本日のときだけ**行う。
- 各バス区間について `realtimeTripLookup.findLiveAssignment(feedId, routeId, tripId, tripDepartureTime)` で当日の担当割り当てを探す。
- 見つかれば `buildBusEntry()` で停車進捗・到着予測・車両位置を取得し、
  **バス停名の一致**で乗車停・降車停・各通過停に予測時刻／通過実績を割り当てる（`busStopApproaching.js` と同じ方針。DBの `stops` は標柱を持たないため名前一致が唯一の接点）。
- 予測が引けた区間だけ `realtime.hasRealtime = true` とし、引けなくても**定刻で成立させる**（区間ごと落とさない）。
- 同一割り当ての取得はリクエスト内でキャッシュし、同じ便を何度も引かない。

## 6. 画面仕様（`frontend/routesearch.js`）

### 6.1 URL設計

時刻表検索・バス停検索と同じくHistory API（パス）でルーティングする。
検索条件をURLに持たせることで、**`/busstop` へ移動して戻ってきても検索結果が復元される**（要望3の副作用対策）。

```
/routesearch                                                    検索フォーム
/routesearch?from={stopKey}&to={stopKey}&date=YYYY-MM-DD&time=HH:MM           結果
```

- メニューの「ルート検索」は `/routesearch` へのリンク（`data-spa`）にする。
- 旧ハッシュ `#/search` は `/routesearch` へリダイレクトする（既存のブックマーク対策）。

### 6.2 検索フォーム

- 出発地／目的地：インクリメンタル候補表示（ひらがな・ローマ字対応、`/api/route-search/stops`）。候補には路線カラーのチップを並べる。
- 入れ替えボタン（現行同等）。
- **日付**：`<input type="date">`＋クイックボタン「今日／明日／平日／土曜／日祝」（時刻表検索の `renderCalendar` と同じ操作感）。選択中の日付は「8月11日（火）」形式で表示する（要望5）。
- 時刻：`<input type="time">`＋「現在時刻」ボタン（指定時刻以降に出発する経路を探す）。
- 未入力・同一バス停選択などはフォーム内に警告表示（現行同等）。

### 6.3 結果カード（路線カラー基調・要望1）

各経路カードは次の構成にする。

```
┌──────────────────────────────────────────┐
│ ★おすすめ  乗換1回  ●リアルタイム            │  ← バッジ
│ 9:05 → 9:31   26分   ¥400                 │  ← 大きい時刻・所要・運賃
│ ▌▌▌▌▌▌▌▌▌▌  ← 区間ごとの路線カラーで塗った所要時間バー
│ ● 松本バスターミナル 3番のりば              │
│ ┃ [横田信大循環線] 信州大学前ゆき  8停留所  ¥200
│ ┃  ← 路線カラーの縦帯                       │
│ ● 信大附属前                                │
│ ┊ 徒歩3分（220m）                           │
│ ● 横田町                                    │
│ ┃ [浅間線] 浅間温泉ゆき  4停留所  ¥200      │
│ ● 信州大学前                                │
│  [通過するバス停を見る ▾]                    │
└──────────────────────────────────────────┘
```

- 縦帯・チップ・所要時間バーの色は `route_color` / `route_text_color`。
- 色のコントラストが不足する路線（黄色など）は、時刻表検索と同じ `chipTextColor()` / `routeColorStyle()` を用いて文字色を反転させ、**視認性を必ず確保する**。色が未設定の路線はグレーにフォールバックする。
- 路線カラーの実装は `timetable.js` / `busstop.js` にある関数と同一ロジックを使う（3画面で見た目を揃える）。

### 6.4 バス停タップと通過バス停（要望3）

- カード内の**すべてのバス停名はリンク**であり、`/busstop/{stopKey}` へSPA遷移する。
- 「通過するバス停を見る」を開くと、その区間の**乗車停から降車停までの全通過バス停と通過時刻**を縦のタイムラインで表示する。
  - 乗車停・降車停を強調、途中停留所は淡色。
  - リアルタイムがある場合は、通過済みは実績時刻、未通過は予測時刻を表示し、遅延分数を添える。
  - 各バス停名から `/busstop/{stopKey}` へ遷移できる。
- 区間ヘッダから「この便の全区間（便詳細）」＝ `/timetable/trips/...` へも遷移できる。

### 6.5 リアルタイム表示

- 検索日が本日で、かつ区間にリアルタイムがある場合のみ「● リアルタイム」バッジと遅延分数を表示する。
- 走行中の車両がある区間には現在位置のバス停名（`〜を発車`）を出す。
- 20秒間隔で結果を再取得する（本日の検索時のみ。他日はポーリングしない）。

### 6.6 見つからなかったとき（要望6）

- 段階的フォールバック（7章）の結果として `found:false` になった場合は、理由（`reason`）に応じたメッセージと次の手を出す。
  - `no-service-on-date`：「この日はこの区間を結ぶ便がありません。」＋**次の運行日（8月13日（木））で検索**ボタン。
  - `no-service-at-stop`：「この日は出発地のバス停に発着する便がありません。」＋近くのバス停ボタン。
  - `after-last-bus`：「9:00 以降にこの区間を結ぶ便はありません。」＋**この日の始発（5:40）で検索**ボタン。
  - `stop-not-found`：「一致するバス停が見つかりませんでした。」＋「もしかして」候補ボタン。
- **日付の表記（「8月13日（木）」）は画面側で組み立てる。** サーバーの文言に日付文字列を埋め込むと、`2026-08-13` のような生の表記が画面に出てしまう。サーバーは `suggestion: { kind, date, time }` を返し、ラベルはフロントエンドで作る。

## 7. 「経路が見つからない」を減らすための段階的フォールバック（要望6）

`searchJourneys()` は、結果が0件のあいだ次の順に条件を緩めて再探索する。**どの段階で見つかったかを `relaxation` としてレスポンスに含め、画面に明示する。**

| 段階 | `relaxation` | 条件 | 画面表示 |
|---|---|---|---|
| 1 | `normal` | 探索窓6時間・乗換2回まで・徒歩400m | （通常） |
| 2 | `wide-window` | 探索窓を30時間へ拡張 | 「指定時刻からしばらく後に出発する便を含みます」 |
| 3 | `walk-transfer` | 徒歩800m・乗換3回まで | 「徒歩での乗り継ぎ（最大800m）を含む経路です」 |
| 4 | （`found:false`） | 翌日以降7日以内で、最初に経路が成立する日を探す（各日は始発時刻から探索） | 「この日はこの区間を結ぶ便がありません」＋次の運行日ボタン |

5.2の翌日サービス取り込みにより、段階2の時点で「翌朝の始発」が候補に入る。その場合は
`relaxationNote` を「指定時刻以降にこの日の便が無いため、翌日の便を表示しています。」に差し替え、
各経路には `departureDayOffset`/`arrivalDayOffset` を付けて画面に「翌日 7:05」「翌日着」と出す。

さらに、探索に入る前の入力解決でも次のフォールバックを行う。

- stopKeyが解決できない → 名前検索の上位3件を候補として全組み合わせ探索（3.2）。
- 出発地と目的地が同一グループ → 400m以内の別グループを候補に加えて再判定（同名で統合された巨大バス停の内側移動を防ぐ）。それでも同一なら明示的にエラー。
- 出発地または目的地に、その日1本も発着が無い → その旨を出し、500m以内の代替バス停を提示する。

## 8. API仕様

### 8.1 `GET /api/route-search/stops`

| クエリ | 内容 |
|---|---|
| `q` | 検索文字列（漢字・かな・ローマ字） |
| `limit` | 最大件数（既定20、上限50） |

レスポンス: `{ "stops": [ 3.1のオブジェクト ] }`

### 8.2 `GET /api/route-search`

| クエリ | 内容 |
|---|---|
| `fromStopKey` / `from` | 出発地 |
| `toStopKey` / `to` | 目的地 |
| `date` | `YYYY-MM-DD`（既定: 本日） |
| `time` | `HH:MM`（既定: 本日なら現在時刻、他日なら05:00） |
| `limit` | 1〜10（既定5） |

レスポンス: 5.5 の構造。見つからない場合は
`{ "found": false, "reason": "...", "message": "...", "suggestion": { … } }`。

**旧APIとの互換性**: 旧 `departureTime` パラメータは `time` の別名として受け付ける。
旧レスポンス（`routes[]`）は廃止し `journeys[]` にする。旧フロントは同時に差し替えるため互換は不要。

### 8.3 変更しないAPI

`/api/stops/search`（DBベースのバス停名検索）は管理用途で残す。`routeSearch.js` にはこの関数だけを残す。

## 9. 性能・キャッシュ

- GTFSインデックスは既存のもの（30分TTL・GTFS更新時に無効化）をそのまま共用する。追加のメモリコストは
  「グループ別 stop_times 逆引き」「徒歩接続表」「運賃インデックス」のみで、いずれも数MB以下。
- 日付ごとの探索用データ（その日に有効な便の一覧）は最大8日ぶんをLRUキャッシュする。インデックスが作り直されたら破棄する。
- 1回の探索は最大10回のRAPTOR実行（5.4）。1回の実行は「マーク済みバス停 × その停留所の発車便 × 便の残り停留所」で、
  現行フィード規模（バス停約1,000・便約1,000・stop_times約40,000）では数十ミリ秒で完了する見込み。
- リアルタイム重ね合わせのDBアクセスは、割り当て単位でリクエスト内キャッシュする。

## 10. 移行・後方互換に関する注意

- **`REQUIRED_GTFS_FILES` に運賃ファイルを足さない**（4.1）。
- **`gtfsTimetable.js` の既存の公開関数のシグネチャは変えない。** 追加するのは新しいエクスポートとインデックスのフィールドのみ。
  時刻表検索・バス停検索・バス停マップの挙動を変えてはならない。
- **DB側の3つの曜日区分ロジック（`getDayType` / `getActiveServiceIds` / `getActiveServices`）は統合しない。**
  経路検索は時刻表検索用の `getActiveServices()` を使う（任意日付・有効期間チェックが必要なため）。
- 旧 `routeSearch.js` の経路探索関数（`searchStopCandidates` / `resolveStopNameCandidates` / `findLegCandidates` / `searchDirectRoutes` / `searchTransferRoutes` / `searchRoutes`）は削除する。README §8 も差し替える。
