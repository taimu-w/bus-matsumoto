# 経路検索機能の仕様（`services/gtfsRouteSearch.js` / `frontend/routesearch.js`）

## 1. 概要

経路検索は、時刻表検索と同じGTFSインメモリインデックス（`gtfsTimetable.js`）を直接探索するRAPTOR型の
エンジンです。**リアルタイム運行状況とはデータ経路が完全に独立**しており、探索はDBを一切見ません。
リアルタイム情報（遅延・予測時刻・車両位置）は、確定した経路に`realtimeTripLookup.js`経由で後から
重ねます（バス停検索の「接近中のバス」と同じ設計）。

このドキュメントはアーキテクチャ・探索アルゴリズム・APIの詳細です。細部の定数・挙動は必ず実装コード
（`services/gtfsRouteSearch.js`）を正としてください。章番号（`5.6` など）は他ドキュメントからの参照でも
使われています。

---

## 2. アーキテクチャ

```
                     ┌──────────────────────────────┐
                     │ gtfsTimetable.js             │  GTFSファイル直読みの
                     │  index (30分TTL/更新時無効化) │  インメモリインデックス
                     │   groups / stops / trips /   │  （時刻表検索・バス停検索と共用）
                     │   stopTimesByTrip / services │
                     └──────────────┬───────────────┘
                                    │ getIndex()
       ┌────────────────────────────┼────────────────────────────┐
       │                            │                            │
┌──────┴───────┐          ┌─────────┴──────────┐        ┌────────┴─────────┐
│ gtfsFare.js  │          │ gtfsRouteSearch.js │        │ realtimeTripLookup│
│ 運賃インデックス│◀────────│  経路探索エンジン    │───────▶│  当日の運行実績     │
│ (fare_*.txt) │  運賃照会  │  （RAPTOR型）       │ 実測重ね │  (daily_trips)    │
└──────────────┘          └─────────┬──────────┘        └──────────────────┘
                                    │
                            /api/route-search
                                    │
                          frontend/routesearch.js
```

- **探索（どの便に乗るか）はGTFSインデックスだけで完結する。** DBが落ちていても、当日便が未生成でも、任意の日付で経路が出る。
- **リアルタイムは「今日」を検索したときだけ**、確定した経路に対して後から重ねる。重ね合わせに失敗しても定刻表示で成立させる（soft-fail）。
- 運賃は`gtfsFare.js`が`fare_attributes.txt` / `fare_rules.txt`（任意ファイル）から引く。
- `routeSearch.js`には`/api/stops/search`用の`searchStops()`だけを残し、経路探索は`gtfsRouteSearch.js`が担う。

## 3. バス停の指定

### 3.1 候補検索

`GET /api/route-search/stops?q={文字列}&limit={n}`

- `gtfsTimetable.searchStops()` をそのまま使う。すなわち**漢字・ひらがな・カタカナ・ローマ字（大文字小文字・全半角不問）**に対応し、前方一致を優先して部分一致も返す。時刻表検索・バス停検索と**まったく同じ検索体験**にする。
- 返す `stopKey` は**GTFSインデックスのグループキー**（`/busstop/{stopKey}` や `/timetable/stops/{stopKey}` と同じ値）。
  - これにより、経路検索の結果から `/busstop` へ**IDのまま**遷移できる（名前による橋渡しは不要）。
- レスポンス（`stops[]`）:

```jsonc
{
  "stopKey": "100",
  "name": "松本バスターミナル",
  "kana": "まつもとばすたーみなる",      // nameHiragana
  "romaji": "Matsumotobasutaminaru",
  "platformCount": 6,
  "lat": 36.2302, "lon": 137.9667,
  "routes": [ { "routeId": "11", "feedId": "guruttomatsumotobus1",
                "name": "横田信大循環線", "shortName": "", "color": "FF9900", "textColor": "FFFFFF" } ]
}
```

### 3.2 自由文字列（候補未選択）での検索

候補を選ばずに検索した場合は、同じ `searchStops()` で先頭最大3件のバス停を候補とみなし、
**その全組み合わせ**を探索してもっとも良い経路を返す。あいまい一致で検索したことは結果画面に明示する。

### 3.3 バス停の同一視

GTFSインデックスの統合ルール（`gtfsTimetable.js` の `buildGroups()`：同一ベースID＋同名／同名かつ400m以内は1件へ統合）をそのまま使う。
複数フィードに同じ物理バス停が別IDで入っているケースはこの時点で吸収済みであり、
**「アルピコのバスで着いて松本市営のバスに乗り継ぐ」ような経路が同一バス停の乗換として自然に見つかる。**

## 4. 運賃

### 4.1 データの取得

`fare_attributes.txt` / `fare_rules.txt` は `gtfsFeedManager.js` の `OPTIONAL_GTFS_FILES` に含まれ、
存在すれば展開先へ配置される。

- **`REQUIRED_GTFS_FILES` には絶対に追加しない。** 持たないフィードが1つでもあると全フィードのGTFS更新が止まる（CLAUDE.md 既知の注意点）。
- 読み込みは `readCsvIfExists()` を使い、無ければ「運賃不明」として機能全体は成立させる。

### 4.2 運賃インデックス（`gtfsFare.js`）

フィードごとに以下を構築し、`gtfsTimetable` のインデックスと同じTTL・無効化タイミングで作り直す。

- `fareById`: `fare_id` → `{ price, currency, paymentMethod, transfers }`
- `rulesByRoute`: `route_id`（空文字＝全路線）→ ルール配列 `{ fareId, originId, destinationId, containsId }`
- `zoneByStopId`: `stop_id` → `zone_id`（`stops.txt` の `zone_id`。松本のデータでは `zone_id = stop_id`）

### 4.3 運賃の決定ルール

`lookupFare(feedId, routeId, boardStopId, alightStopId)`

1. 乗車・降車の `stop_id` から `zone_id` を求める。
2. 対象ルールを「その路線のルール」＋「route_id が空のルール（全路線共通）」とする。
3. 各ルールについて、`origin_id`／`destination_id` が空 or 一致していれば適用可能とする（GTFS仕様どおり）。
4. 適用可能なルールが複数ある場合は**より限定的なもの**を優先する。優先度は
   `origin+destination 指定 > どちらか一方だけ指定 > 両方とも空`、同順位なら**運賃の安い方**を採用する。
5. 1件も該当しない場合は `null`（＝運賃不明）を返す。**推測はしない。**

`contains_id` は今回のデータに存在しないため未対応とする（存在しても無視して他の条件だけで判定する）。

### 4.4 表示仕様

- 区間（leg）ごとに運賃を表示し、経路全体の合計も表示する。
- 乗換がある場合は単純合計とする（`fare_attributes.transfers = 0`＝乗継割引なし、というデータどおりの扱い）。
- 1区間でも運賃不明があれば、合計に「一部不明」を明示する（合計を出さないのではなく、判明ぶんの合計＋注記）。
- 画面に「運賃はGTFSデータに基づく目安です。実際の運賃は事業者にご確認ください。」と常時注記する。

## 5. 経路探索エンジン（`gtfsRouteSearch.js`）

### 5.1 入力

| パラメータ | 内容 | 既定値 |
|---|---|---|
| `fromStopKey` / `from` | 出発地（stopKey または自由文字列） | 必須 |
| `toStopKey` / `to` | 目的地（stopKey または自由文字列） | 必須 |
| `date` | 検索する日付（`YYYY-MM-DD`）＝**カレンダーで選択した日** | 本日（JST） |
| `time` | 基準時刻（`HH:MM`）。`timeMode` により出発時刻／到着時刻が切り替わる | 出発時刻指定：現在時刻（本日のとき）／`05:00`（他日のとき）<br>到着時刻指定：現在時刻＋1時間（本日のとき）／`12:00`（他日のとき） |
| `timeMode` | `departure`＝この時刻**以降に出発**／`arrival`＝この時刻**までに到着** | `departure` |
| `limit` | 返す経路数 | 5 |
| `maxTransfers` | 詳細設定：乗換回数の上限（`0`＝乗り換えなし）。5.8 | 指定なし |
| `allowWalkTransfer` | 詳細設定：徒歩での乗り継ぎを使うか。5.8 | `true` |
| `minTransferMinutes` | 詳細設定：乗り換えに要求する最低の余裕時間（分）。5.8 | `1` |

`timeMode=arrival`（「◯時までに着きたい」）は5.6で述べる**逆向き探索**で処理する。
未指定・不正値は必ず `departure` として扱い、従来のクライアントの挙動を変えない。
詳細設定（5.8）も同様に、未指定・不正値はすべて既定＝従来の探索条件に落とす。

### 5.2 運行日の扱い

`gtfsTimetable.getActiveServices(index, dateStr)`（`calendar.txt` の有効期間＋曜日、`calendar_dates.txt` の例外を反映）で
その日に有効な `service_id` を求め、その `service_id` を持つ便だけを探索対象にする。

**GTFSデータの有効期間外の日付**: `common.gtfsValidity`（`describeDateValidity()`）を成否にかかわらず
返す。選択日が現在のGTFSの有効期間（全有効フィードの union）外なら `outOfRange:true` とし、画面が
「ダイヤ改正でこの日の運行が変わる可能性がある」旨をポップアップで出す。期間の求め方・レスポンス形状は
[timetable-search.md](timetable-search.md)「GTFSデータの有効期間外の注意喚起」を参照。

**日跨ぎの扱い**（見つからない経路を減らすため）:

- 前日サービスの24時超え便（例: 前日の `24:30` 発）を **−86400秒シフト**して当日の `0:30` として取り込む。
  → 深夜0時台の検索で「昨日のダイヤの深夜便」が正しく出る。
- 翌日サービスの便を **+86400秒シフト**して取り込む。
  → 終バス後に検索したとき、翌朝の始発が「翌日 5:40」として出る（同日の候補があればそちらが必ず先に選ばれる）。
- 表示上、`86400`秒以上の時刻は `翌日 5:40` のように日付を添える。

### 5.3 探索アルゴリズム

RAPTOR（ラウンド型）方式を採用する。ダイクストラではなくRAPTORにするのは、
**「乗換回数ごとの最良解（パレート最適解）」が1回の実行で同時に得られる**ため、
「直通は遅いが乗換1回なら早い」といった複数案を自然に列挙できるからである。

```
τ[k][stop] : k回乗車したあとに stop へ到着できる最早時刻
ラウンド0 : τ[0][出発地] = 基準時刻。徒歩接続で近傍バス停へ展開。
ラウンドk : 直前ラウンドで更新されたバス停から乗車できる便を走査し、
            その便の以降のバス停の到着時刻を更新する。
            更新されたバス停から徒歩接続を relax する。
```

- **乗車可能条件**: `pickup_type != 1` かつ 便の発車時刻 ≥ そのバス停への到着時刻 ＋ 乗換余裕（同一バス停 60秒、徒歩接続は徒歩所要時間）。ラウンド1（最初の乗車）では乗換余裕を課さない。
- **降車可能条件**: `drop_off_type != 1`。
- **徒歩接続（footpath）**: バス停グループ間の**直線距離**が `WALK_RADIUS_METERS`（既定400m、フォールバック時800m）以内なら徒歩で乗換できるものとする。**乗り継ぎ可否の判定は直線距離**だが、**徒歩時間は `utils/geo.js` の `estimateWalkSeconds()`**（直線距離に迂回係数・信号待ちを織り込んだ推定。距離が伸びるほど迂回・信号バッファを増やす区分線形。最低60秒）を使う。緯度経度のグリッドで近傍だけを比較し、半径ごとに1度だけ作ってキャッシュする。
  - **これが「経路が見つからない」の最大の対策**である。現行は同名バス停でしか乗り換えられない。
  - **徒歩の連鎖（徒歩→徒歩）は禁止する。** 同一ラウンド内で既に徒歩ラベルが付いたバス停からは再relaxしない。許すと「4分歩いて5分歩いて…」という非現実的な経路が最速解になる。
  - 1経路あたりの徒歩の合計が `MAX_TOTAL_WALK_MINUTES`（25分）を超える案は、他に候補があるなら出さない。
- **枝刈り**: 目的地への現在の最良到着時刻を超える更新は捨てる。基準時刻＋探索窓（既定6時間）より後に出発する便は見ない。
- **最大ラウンド数**: 3（＝乗換2回まで）。フォールバック時は4（乗換3回まで）。
- **frequencies.txt** 由来の便は、`gtfsTimetable` と同じく仮想便へ展開してから探索対象に入れる（現行フィードには存在しないが、将来フィードが変わっても壊れないようにする）。

### 5.4 複数候補の作り方

1. 1回の探索で、ラウンドごと（乗換0回／1回／2回）の最良経路をすべて取り出す。
2. 先頭区間の発車時刻を1分進めて再探索し、これを `limit` 件そろうまで最大12回繰り返す（＝「次の便」「その次の便」が並ぶ）。
3. **徒歩接続を使わない探索も必ず実行し、結果に混ぜる。** 徒歩を許すと「1駅手前で降りて歩く」方が最速になり、バスだけで完結する案が枝刈りで消えてしまう。利用者はふつう歩かない案も知りたいので、両方を候補に残す。
4. 同一の便構成（全区間の `tripId` と乗降バス停が同じ）は重複として除外する。
5. 並び順は**到着時刻の早い順**、同着なら乗換回数の少ない順。
6. `isRecommended`（おすすめ）は `到着時刻 + 乗換回数×5分 + 徒歩時間×0.5` が最小の1件に付ける。
   単純な最速ではなく「乗換が少なく歩かない経路」を適度に優遇するため。

### 5.6 到着時刻指定（逆向きRAPTOR）

`timeMode=arrival` のとき、`runRaptorReverse()` が時間軸を反転させた探索を行う。
探索の目的は最早到着の最小化ではなく、**最遅出発の最大化**（＝「何時に出れば間に合うか」）である。

```
τ[k][stop] : あと k 回バスに乗れば目的地に間に合う、そのバス停の最遅出発時刻
ラウンド0 : τ[0][目的地] = 到着期限。徒歩接続で近傍バス停へ展開（目的地へ歩く区間）。
ラウンドk : 直前ラウンドで更新されたバス停に「τ までに到着する便」を探し、
            その便を遡って手前のバス停の最遅出発時刻を更新する。
```

順向き（`runRaptor`）との対応は次のとおり。**この対称性を崩すと「出発時刻指定では出るのに
到着時刻指定では出ない区間」が生まれる**ので、片方だけを変更しないこと。

| 順向き（出発時刻指定） | 逆向き（到着時刻指定） |
|---|---|
| 最早到着を最小化 | 最遅出発を最大化 |
| 乗車できる発車の索引（`boardingsByGroup`、発車時刻順） | 降車できる到着の索引（`alightingsByGroup`、到着時刻順） |
| 便を先へ走査（`pickup_type != 1` で乗り、`drop_off_type != 1` で降りる） | 便を手前へ遡る（採用条件は同一） |
| 乗換余裕はラウンド1（最初の乗車）で免除 | 乗換余裕はラウンド1（最後の降車）で免除 |
| 基準時刻＋探索窓で打ち切り | 基準時刻−探索窓で打ち切り |
| 目的地の最良到着で枝刈り | 出発地の最良出発で枝刈り |
| 次候補は基準時刻を1分進めて再探索 | 次候補は到着期限を1分戻して再探索 |
| 並び順は到着の早い順 | 並び順は**出発の遅い順**（指定時刻に近い便から） |
| おすすめは `到着時刻 + 乗換×5分 + 徒歩×0.5` 最小 | おすすめは `−出発時刻 + 乗換×5分 + 徒歩×0.5` 最小 |

- **降車索引（`alightingsByGroup`）は到着時刻指定を初めて使うまで構築しない。** 出発時刻指定しか
  使わない場合に余分なメモリと構築時間を負わせないため。GTFSインデックスが作り直されれば一緒に破棄される。
- **徒歩区間の時刻は「バスを降りた直後」に寄せ直す**（`normalizeReverseLabels()`）。逆向き探索は
  すべての区間を「次のバスにぎりぎり間に合う最遅の時刻」で組むため、そのままだと
  「降車後しばらく待ってから歩き出す」表示になる。ただし**先頭の徒歩（出発地→最初のバス停）は
  最遅のまま**にする。到着時刻指定では「家を何時に出ればよいか」がそのまま答えになるため。
- **観光スポットを目的地にした場合**は、バス停ごとに「スポットまでの徒歩時間」を差し引いた時刻を
  到着期限にする（バス停に着いた時刻ではなく**スポットに着いた時刻**が指定時刻に間に合う必要があるため）。
- 日跨ぎは5.2のとおり前日・当日・翌日の3シフトをそのまま使う。到着時刻指定では
  **出発が前日になる**ことがあり（例：0:30着に間に合うのは前日22:39発）、`departureDayOffset` は負になる。
  この場合リアルタイムは重ねない（当日の `daily_trips` とは別の日の便のため）。
- **既知の近似**：1バス停につきラウンドごとに1ラベルしか持たない（順向きと同じ）ため、
  徒歩ラベルがわずかに早いバス乗車のラベルを塞ぐと、理論上の最遅出発より数分早い経路を返すことがある。
  返す経路自体は必ず指定時刻までに到着する妥当な経路であり、**安全側（早めに出発する側）にしかぶれない**。
  順向き探索が持つ近似とまったく同じ性質であり、両者の対称性を保つためにあえて解消していない。

### 5.7 リアルタイムの重ね合わせ

- 検索日が**本日のときだけ**行う。
- 各バス区間について `realtimeTripLookup.findLiveAssignment(feedId, routeId, tripId, tripDepartureTime)` で当日の担当割り当てを探す。
- 見つかれば `buildBusEntry()` で停車進捗・到着予測・車両位置を取得し、
  **バス停名の一致**で乗車停・降車停・各通過停に予測時刻／通過実績を割り当てる（`busStopApproaching.js` と同じ方針。DBの `stops` は標柱を持たないため名前一致が唯一の接点）。
- 予測が引けた区間だけ `realtime.hasRealtime = true` とし、引けなくても**定刻で成立させる**（区間ごと落とさない）。
- 同一割り当ての取得はリクエスト内でキャッシュし、同じ便を何度も引かない。
- **管理画面「リアルタイム休止」中の路線を含む区間は重ね合わせをスキップし、定刻のまま返す**
  （`findLiveAssignment()` が休止路線に `null` を返すため。加えて `attachRealtime()` が
  `leg.realtimeSuspended` / `journey.realtimeSuspended` を立て、画面が「定刻表示」の注記を出す）。
  **探索・運賃・おすすめ判定・並び順は影響を受けない**（通常どおりの検索は認める）。詳細は
  [realtime-suspension.md](realtime-suspension.md)。

### 5.8 詳細設定（「乗り換えなし」で探す、など）

利用者が探索条件そのものを絞り込めるようにする。**既定値は従来の探索条件そのもの**であり、
何も指定しなければ結果はこの機能の追加前とまったく同じになる。

| 設定 | パラメータ | 値 | 既定 |
|---|---|---|---|
| 乗り換え回数 | `maxTransfers` | 指定なし／`0`（乗り換えなし）／`1`／`2`（上限は`MAX_ROUNDS_RELAXED - 1`＝3） | 指定なし |
| 徒歩での乗り継ぎ | `allowWalkTransfer` | `true`／`false` | `true` |
| 乗り換えの余裕時間 | `minTransferMinutes` | 1〜15（分） | 1 |

実装上の要点:

- 正規化は `normalizeSearchPreferences()` 1箇所に集約する。**未指定・空文字・不正値・範囲外はすべて既定へ落とす。**
  旧クライアントや、詳細設定を付けずに保存された既存のURL・お気に入りの挙動を変えないため。
- **詳細設定は探索条件を「絞る方向」にだけ効かせる**（`applyPreferencesToStep()`）。
  段階的フォールバック（7章）は0件のとき条件を緩めるが、利用者が明示した上限は超えない
  （「乗り換えなし」で検索したのにフォールバック段階3で乗換つきの案が出る、という事故を防ぐ）。
  - `maxTransfers` → `maxRounds = min(段階のmaxRounds, maxTransfers + 1)`（ラウンド数＝乗車回数）
  - `allowWalkTransfer=false` → `radiusMeters = 0`（徒歩接続表を空にする＝乗り継ぎだけでなく
    出発地・目的地から近隣バス停へ歩く展開も行わない）
  - `minTransferMinutes` → `runRaptor` / `runRaptorReverse` の乗換余裕（`MIN_TRANSFER_SECONDS` の代わり）。
    **リアルタイム反映後の「乗換に間に合わない可能性」判定（`flagTransferRisks()`）にも同じ値を渡す。**
    探索時と判定時で余裕が食い違うと、探索が通した乗換をその場で警告することになる。
- 条件を絞ると段階1〜3が同じ探索条件に潰れることがある（例：徒歩なし＋乗換0回では段階2と段階3が一致）。
  `runRelaxationSearch()` は同一条件の再探索をスキップする。徒歩なしのときは
  「徒歩なしの結果を混ぜる」マージも同じ探索の繰り返しになるため行わない。
- **0件のときは「詳細設定が原因か」を切り分ける。** 既定条件で探し直して1件でも見つかるなら
  `reason: 'no-route-with-conditions'`・`canRelaxPreferences: true` を返し、画面に
  「詳細設定を解除して検索」の導線を出させる。日付や時刻を変えさせる案内（6.6）は的外れになるため。
  既定条件でも0件なら従来どおり6.6の応答へ進む。このとき案内する「その日の始発」「次の運行日」も
  **詳細設定を満たす経路で探す**（満たさない日を提示しても利用者は再検索できない）。
- レスポンスには成否にかかわらず `preferences`（`maxTransfers` / `allowWalkTransfer` /
  `minTransferMinutes` / `isDefault`）を含める。画面が適用中の条件を復元・表示するために使う。

## 6. 画面仕様（`frontend/routesearch.js`）

### 6.1 URL設計

時刻表検索・バス停検索と同じくHistory API（パス）でルーティングする。
検索条件をURLに持たせることで、**`/busstop` へ移動して戻ってきても検索結果が復元される**。

```
/routesearch                                                    検索フォーム
/routesearch?from={stopKey}&to={stopKey}&date=YYYY-MM-DD&time=HH:MM           結果（経路一覧）
/routesearch?…&time=HH:MM&timeMode=arrival                      結果（到着時刻指定）
/routesearch?…&journey=N                                        経路詳細（一覧のN件目・0始まり）
```

`timeMode` は**到着時刻指定のときだけURLに載せる**。既定（出発時刻指定）で余計なパラメータを
増やすと、既存のブックマーク・お気に入りルートのURLと表記が食い違うため。

`journey` も**経路詳細を開いているときだけ載せる**（一覧のURLは従来と同じ形のまま）。
これにより詳細画面のリロード・共有・ブラウザの戻るがそのまま効く。
`journey` の値は一覧の並び順であって経路の恒久的なIDではないため、**指定の経路が
存在しないとき（古いURL・リアルタイム更新で件数が減った場合）は`replaceState`で
`journey`を外して一覧を表示する**（エラーにしない）。日付・時刻・バス停を変える再検索
（クイックボタン・「近くのバス停で検索」など）では必ず`journey`を外して一覧から始める。

- メニューの「ルート検索」は `/routesearch` へのリンク（`data-spa`）にする。
- 旧ハッシュ `#/search` は `/routesearch` へリダイレクトする（既存のブックマーク対策）。
- お気に入りルートのURLには`journey`を含めない（開いた時点で検索し直して一覧を出す）。

### 6.2 検索フォーム

- 出発地／目的地：インクリメンタル候補表示（ひらがな・ローマ字対応、`/api/route-search/stops`）。候補には路線カラーのチップを並べる。
- 入れ替えボタン（現行同等）。
- **日付**：`<input type="date">`＋クイックボタン「今日／明日／平日／土曜／日祝」（時刻表検索の `renderCalendar` と同じ操作感）。選択中の日付は「8月11日（火）」形式で表示する。
- 時刻：**「出発時刻／到着時刻」の切り替えボタン**＋`<input type="time">`＋「現在時刻」ボタン。
  切り替えると（日付のクイックボタンと同じく）出発地・目的地が入力済みならその場で検索し直す。
  どちらを指定しているかは切り替えボタンの選択状態と、直下の説明文（「指定した時刻までに到着する経路を、
  遅く出発できる順に探します。」）の両方で示す。**時刻欄の値は切り替えても書き換えない**
  （「9:00発」で調べたあと「9:00着」で調べ直す操作を1タップでできるようにするため）。
- **詳細設定**（5.8）：`<details>` の折りたたみパネル。**既定では閉じていて、既定値のままなら
  検索条件は従来とまったく同じ**（この機能を知らない利用者の体験は変わらない）。
  「乗り換え回数」「徒歩での乗り継ぎ」「乗り換えの余裕時間」を選択ボタンで指定し、
  日付・時刻の切り替えと同じく出発地・目的地が入力済みならその場で検索し直す。
  - 値は hidden input（`rs-maxtransfers` / `rs-walktransfer` / `rs-transfermargin`）に持たせ、
    選択状態のスタイルだけをその場で塗り替える。**フォーム全体を描き直さないこと**
    （入力中のテキストや候補リストが消えるため）。
  - 条件が入っていればパネルは開いた状態で描画し、見出しに要約（「乗り換えなし」など）を出す。
    ただし利用者が自分で閉じたらその意思を優先する（`advancedOpen` が `null` のときだけ自動で開く）。
  - 既定値の項目はURL・APIクエリ・お気に入りURLに**載せない**（`appendPreferenceParams()`）。
    従来のURL・ブックマーク・お気に入りと同じ形を保ち、往復で条件が増えないようにするため。
  - 開閉の目印（「開く▾／閉じる▴」）は `style.css` の `#rs-advanced[open]` で切り替える。
    TailwindのCDNビルド依存の `group-open:` は使わない。
- 未入力・同一バス停選択などはフォーム内に警告表示（現行同等）。

### 6.3 結果の2階層（経路一覧 → 経路詳細・路線カラー基調）

結果は**「一覧で選ぶ」→「1件の詳細を読む」の2画面**に分ける。乗り換え時刻や通過バス停まで
すべてを一覧に並べると、5件並んだだけで画面が縦に長くなり、経路を見比べられなくなるため。

#### 6.3.1 経路一覧（`renderJourneyListItem`）

1件あたり**選ぶための情報だけ**を載せ、カード全体が詳細を開くボタンになる。

```
┌──────────────────────────────────────────┐
│ ★おすすめ  直通  徒歩3分  ●リアルタイム反映   │  ← バッジ（おすすめ・直通/乗換回数・徒歩）
│ 9:00 → 9:19   19分              ¥270      │  ← 出発／到着時刻・所要時間・運賃
│ ▌▌▌▌▌▌▌▌▌▌  ← 区間ごとの路線カラーで塗った所要時間バー（徒歩は斜線）
│ [信大横田循環線] › 徒歩3分          詳細 › │  ← 乗車する路線のチップ列
└──────────────────────────────────────────┘
```

- カードは`<button>`1つとし、中にリンク（`<a>`）を置かない（入れ子の操作要素を作らない）。
- ヘッダー直下に「経路をタップすると、乗り換え時刻や通過するバス停を表示します。」と明示する。
- お気に入りルートの登録行（`rs-fav-row`）は一覧側だけに置く（検索条件に対する操作のため）。
- **一覧の上下に「1本前 / 1本後」ボタン（`nudgeRowHtml()` / `nudgeTarget()`）を置く。** 先頭経路（`journeys[0]`）を
  基準に1本ぶんずらして検索し直す。
  - 1本後：先頭経路の**最初のバス区間の発車**の1分後以降を、`timeMode=departure`で再検索。
  - 1本前：先頭経路の**到着**の1分前までに到着、を`timeMode=arrival`で再検索。
    出発時刻指定の探索は時間軸を巻き戻せない（同じ便がまた先頭に出るだけ）ため到着時刻指定へ切り替える。
    結果ヘッダーの表記（「◯◯までに到着」）・並び順もそれに追従する（時刻表アプリの「前の時刻」と同じ挙動）。
  - `date`/`time`/`timeMode`をURLへ載せて`navigate()`（pushState）するだけなので、**ブラウザの戻るで直前の
    検索結果へ帰れる**。リロード・共有も従来どおり効く。アンカーは定刻ベースの通算秒（日跨ぎ・前日で
    86400超え/負にもなる）で計算し、`shiftDate()`で日付、`secondsToHhmm()`で時刻へ戻す。
  - ずらした先に便が無ければ従来どおり6.6の「見つからない」応答（＋始発などの導線）を表示する。

#### 6.3.2 経路詳細（`renderJourneyDetail`）

一覧でタップした1件について、**乗り換え時刻・通過バス停・リアルタイム・便詳細への導線**を出す。
検索フォームは表示せず（1件の情報に集中させる）、上端に「‹ 経路一覧へ戻る」、
ヘッダーに「出発地 → 目的地／日付・基準時刻／N件中M件目」、下端に「前の経路／次の経路」を置く。

```
┌──────────────────────────────────────────┐
│ ★おすすめ  乗換1回  ●リアルタイム            │  ← バッジ
│ 9:05 → 9:31   26分   ¥400                 │  ← 大きい時刻・所要・運賃
│ ▌▌▌▌▌▌▌▌▌▌  ← 区間ごとの路線カラーで塗った所要時間バー
│ ● 松本バスターミナル 3番のりば              │
│ ┃ [横田信大循環線] 信州大学前ゆき  8停留所  ¥200
│ ┃  ← 路線カラーの縦帯                       │
│ ● 信大附属前                                │
│ ┊ 徒歩3分（220m）                           │
│ ● 横田町                                    │
│ ┃ [浅間線] 浅間温泉ゆき  4停留所  ¥200      │
│ ● 信州大学前                                │
│  [通過するバス停を見る ▾]                    │
├──────────────────────────────────────────┤
│ ‹ 前の経路（9:00発） │ 次の経路（9:10発）›   │
└──────────────────────────────────────────┘
```

- 「経路一覧へ戻る」は`smartBack()`（app.js）で**ブラウザの戻ると同じ動き**にする。一覧のスクロール
  位置と検索フォームの入力がそのまま戻るため。詳細URLを直接開いた・リロードした場合だけ一覧URLへ遷移する。
- **「前の経路／次の経路」は`replaceState`で移動する**（履歴を積まない）。pushStateにすると詳細を
  たどった回数ぶん戻る操作が必要になり、「戻る＝一覧」という関係が崩れる。
- 「経路一覧へ戻る」は読み込み中・検索失敗時にも押せるよう、結果コンテナ（`#rs-result`）の外に置く。
- 詳細は一覧と**同じAPIレスポンスのN件目**を描くだけで、詳細専用のAPIは持たない
  （リアルタイムの重ね合わせも一覧とまったく同じ結果になる）。

#### 6.3.3 共通（路線カラーと共用関数）

- 縦帯・チップ・所要時間バーの色は `route_color` / `route_text_color`。
- 色のコントラストが不足する路線（黄色など）は、時刻表検索と同じ `chipTextColor()` / `routeColorStyle()` を用いて文字色を反転させ、**視認性を必ず確保する**。色が未設定の路線はグレーにフォールバックする。
- 路線カラーの実装は `timetable.js` / `busstop.js` にある関数と同一ロジックを使う（3画面で見た目を揃える）。
- バッジ（`journeyBadges()`）・運賃文言（`journeyFareText()`）・所要時間バー（`renderDurationBar()`）・
  ヘッダーの地点名（`endpointHeadingHtml()`）は一覧と詳細で**同じ関数を共用する**。同じ経路が
  2画面で違う見た目・違う運賃表記になるのを防ぐため。

### 6.4 バス停タップと通過バス停

- **経路詳細**の**すべてのバス停名はリンク**であり、`/busstop/{stopKey}` へSPA遷移する（一覧のカードはボタン1つなのでリンクを持たない）。
- 「通過するバス停を見る」を開くと、その区間の**乗車停から降車停までの全通過バス停と通過時刻**を縦のタイムラインで表示する。
  - 乗車停・降車停を強調、途中停留所は淡色。
  - リアルタイムがある場合は、通過済みは実績時刻、未通過は予測時刻を表示し、遅延分数を添える。
  - 各バス停名から `/busstop/{stopKey}` へ遷移できる。
- 区間ヘッダから「この便の全区間（便詳細）」＝ `/timetable/trips/...` へも遷移できる。

### 6.5 リアルタイム表示

- 検索日が本日で、かつ区間にリアルタイムがある場合のみ「● リアルタイム」バッジと遅延分数を表示する。
  経路単位のバッジは一覧・詳細の両方に、区間ごとの運行状況・遅延分数は詳細に出す。
- 走行中の車両がある区間には現在位置のバス停名（`〜を発車`）を出す。
- 20秒間隔で結果を再取得する（本日の検索時のみ。他日はポーリングしない）。**経路一覧・経路詳細の
  どちらを開いていてもポーリングする**（詳細は同じAPIレスポンスのN件目を描いているため、
  再取得の処理は共通で、開いている「通過するバス停」（`openLegKeys`）も再描画をまたいで維持する）。

### 6.6 見つからなかったとき

- 段階的フォールバック（7章）の結果として `found:false` になった場合は、理由（`reason`）に応じたメッセージと次の手を出す。
  - `no-service-on-date`：「この日はこの区間を結ぶ便がありません。」＋**次の運行日（8月13日（木））で検索**ボタン。
  - `no-service-at-stop`：「この日は出発地のバス停に発着する便がありません。」＋近くのバス停ボタン。
  - `after-last-bus`：「9:00 以降にこの区間を結ぶ便はありません。」＋**この日の始発（5:40）で検索**ボタン。
  - `before-first-bus`（到着時刻指定のみ）：「5:30 までにこの区間へ到着する便はありません。」
    ＋**この日の最も早い到着（11:18）で検索**ボタン。
  - `stop-not-found`：「一致するバス停が見つかりませんでした。」＋「もしかして」候補ボタン。
- **日付の表記（「8月13日（木）」）は画面側で組み立てる。** サーバーの文言に日付文字列を埋め込むと、`2026-08-13` のような生の表記が画面に出てしまう。サーバーは `suggestion: { kind, date, time }` を返し、ラベルはフロントエンドで作る。

## 7. 「経路が見つからない」を減らすための段階的フォールバック

`searchJourneys()` は、結果が0件のあいだ次の順に条件を緩めて再探索する。**どの段階で見つかったかを `relaxation` としてレスポンスに含め、画面に明示する。**

| 段階 | `relaxation` | 条件 | 画面表示 |
|---|---|---|---|
| 1 | `normal` | 探索窓6時間・乗換2回まで・徒歩400m | （通常） |
| 2 | `wide-window` | 探索窓を30時間へ拡張 | 「指定時刻からしばらく後に出発する便を含みます」 |
| 3 | `walk-transfer` | 徒歩800m・乗換3回まで | 「徒歩での乗り継ぎ（最大800m）を含む経路です」 |
| 4 | （`found:false`） | 翌日以降7日以内で、最初に経路が成立する日を探す（各日は始発時刻から探索） | 「この日はこの区間を結ぶ便がありません」＋次の運行日ボタン |

5.2の翌日サービス取り込みにより、段階2の時点で「翌朝の始発」が候補に入る。その場合は
`relaxationNote` を「指定時刻以降にこの日の便が無いため、翌日の便を表示しています。」に差し替え、
各経路には `departureDayOffset`/`arrivalDayOffset` を付けて画面に「翌日 7:05」「翌日着」と出す。

**詳細設定（5.8）を指定した検索では、この緩和は利用者が指定した上限を超えない。**
段階3で徒歩800m・乗換3回まで緩めるのは「指定なし」のときだけであり、
たとえば「乗り換えなし」を指定していれば全段階を通して乗車1回のままである。
また、詳細設定つきで0件になった場合は、翌日以降を探す前に**既定条件で探し直して原因を切り分ける**
（既定なら見つかるなら `no-route-with-conditions` を返し、設定解除の導線を出す）。

さらに、探索に入る前の入力解決でも次のフォールバックを行う。

- stopKeyが解決できない → 名前検索の上位3件を候補として全組み合わせ探索（3.2）。
- 出発地と目的地が同一グループ → 400m以内の別グループを候補に加えて再判定（同名で統合された巨大バス停の内側移動を防ぐ）。それでも同一なら明示的にエラー。
- 出発地または目的地に、その日1本も発着が無い → その旨を出し、500m以内の代替バス停を提示する。

## 8. API仕様

### 8.1 `GET /api/route-search/stops`

| クエリ | 内容 |
|---|---|
| `q` | 検索文字列（漢字・かな・ローマ字） |
| `limit` | 最大件数（既定20、上限50） |

レスポンス: `{ "stops": [ 3.1のオブジェクト ] }`

### 8.2 `GET /api/route-search`

| クエリ | 内容 |
|---|---|
| `fromStopKey` / `from` | 出発地 |
| `toStopKey` / `to` | 目的地 |
| `date` | `YYYY-MM-DD`（既定: 本日） |
| `time` | `HH:MM`（既定: 5.1のとおり `timeMode` で変わる） |
| `timeMode` | `departure`（既定）／`arrival` |
| `limit` | 1〜10（既定5） |
| `maxTransfers` | 詳細設定：乗換回数の上限（0〜3。未指定＝指定なし） |
| `allowWalkTransfer` | 詳細設定：`false`（または`0`）で徒歩での乗り継ぎを使わない。未指定＝使う |
| `minTransferMinutes` | 詳細設定：乗り換えの余裕時間（1〜15分。未指定＝1） |

レスポンス: 5.5 の構造（＋どちらの指定で検索したかを示す `timeMode`、＋適用中の条件を示す `preferences`、
＋選択日がGTFS有効期間外かを示す `gtfsValidity`）。
見つからない場合は `{ "found": false, "reason": "...", "message": "...", "suggestion": { … } }`。
`suggestion` には `kind`（`first-bus` / `first-arrival` / `next-service-day`）・`date`・`time`・`timeMode` を含める。
**`time` はそのまま検索フォームの時刻欄へ入れられる値**（出発時刻指定なら発時刻、到着時刻指定なら着時刻）とする。
詳細設定が原因で0件だった場合は `reason: "no-route-with-conditions"`・`canRelaxPreferences: true`（5.8）。

`preferences` は成否にかかわらず必ず返す:
`{ "maxTransfers": null|0..3, "allowWalkTransfer": true|false, "minTransferMinutes": 1..15, "isDefault": true|false }`

**パラメータの別名**: `departureTime` は `time` の別名として受け付ける。`arrivalTime` を渡した場合は
`timeMode=arrival` とみなす。`timeMode` 未指定は必ず出発時刻指定として扱う。詳細設定の3パラメータも
未指定なら既定条件で探索する（既存のURL・ブックマーク・お気に入りの挙動を変えないため）。

### 8.3 関連API

`/api/stops/search`（DBベースのバス停名検索）は管理用途で残してある。`routeSearch.js` にはこの関数だけを置く。

## 9. 性能・キャッシュ

- GTFSインデックスは既存のもの（30分TTL・GTFS更新時に無効化）をそのまま共用する。追加のメモリコストは
  「グループ別 stop_times 逆引き」「徒歩接続表」「運賃インデックス」のみで、いずれも数MB以下。
- 日付ごとの探索用データ（その日に有効な便の一覧）は最大8日ぶんをLRUキャッシュする。インデックスが作り直されたら破棄する。
- 1回の探索は最大10回のRAPTOR実行（5.4）。1回の実行は「マーク済みバス停 × その停留所の発車便 × 便の残り停留所」で、
  現行フィード規模（バス停約1,000・便約1,000・stop_times約40,000）では数十ミリ秒で完了する見込み。
- リアルタイム重ね合わせのDBアクセスは、割り当て単位でリクエスト内キャッシュする。

## 10. 実装上の制約

- **`REQUIRED_GTFS_FILES` に運賃ファイル（`fare_attributes.txt` / `fare_rules.txt`）を足さない**（4.1）。
  持たないフィードがあるとGTFS更新が全フィードで止まる。
- **`gtfsTimetable.js` の公開関数のシグネチャは変えない。** 時刻表検索・バス停検索・バス停マップと
  インデックスを共用しているため、これらの挙動を変えてはならない。
- **3つの曜日区分ロジック（`getDayType` / `getActiveServiceIds` / `getActiveServices`）は統合しない。**
  経路検索は時刻表検索用の `getActiveServices()` を使う（任意日付・有効期間チェックが必要なため）。
