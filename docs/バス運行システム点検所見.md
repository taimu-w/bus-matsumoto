GPS取得から当日便生成・車両割り当て・通過判定・遅延計算・ETA予測・統計・API・管理画面までを通しで読み、コード上の欠陥に加えて「コードは動くが実運用で誤判定しうる箇所」を洗い出しました。判定ロジックに関わる所見は、実際に配信されている2フィードのGTFSデータ（計948便）に対して影響件数を実測しています。コードは一切変更していません。

- **照合した仕様**: CLAUDE.md / README.md / docs/
- **所見数**: 41件
- **検証データ**: data gtfs/（948便）

> **追記（対応状況）**: Critical のうち C-1・C-2・C-3・C-4 は対応済みです。stops を物理バス停（gtfs_stop_id）＋通過回数（occurrence）で一意化し、便ごとの実際の停車順は schedule_stop_times に新設した stop_sequence で持つ設計へ変更しました。同じ根から出ていた H-3・H-4 もコード変更なしで解消しています。C-4（プール上のBEGIN/COMMIT）は `client = await pool.connect()` による単一接続への固定で解消しました。High のうち H-7（接近中バス一覧が遅延便を落とす）・H-8（運行日判定のTZ依存）も対応済みです。既存の segment_travel_stats・completed_trips 等の統計・履歴データは引き継がず、マイグレーションで一度だけ空にして作り直す方針を採りました。詳細は各所見の「対応状況」欄、および[03 Critical](#03-critical)・[04 High](#04-high)・[07 着手順の提案](#07-着手順の提案)を参照してください。C-5 をはじめ、それ以外の所見は本追記時点で未対応です。

## 03 Critical

利用者に誤った運行情報が表示される、またはマスタデータが壊れるもの。

### C-1 便の停車順を表す seq_order が非単調・欠番になり、順序に依存する全処理が崩れる

*DB整合性 / 当日便生成 / 循環線*

**該当箇所**
backend/src/db/seed.js:251-307（occurrenceKey の採番）／ backend/src/db/schema.sql:42-55（stops UNIQUE (route_id, direction_id, seq_order)、schedule_stop_times に stop_sequence 列が無い）／ 影響先は dailyTripBuilder.js:38-56, 234、tripAssignment.js:166-217、passDetection.js:126-203、finishService.js:35-46、etaPredictor.js:180-395、realtimeTripLookup.js:76-94

**問題の内容**

seq_order は「(route_id, direction_id, service_id) グループに属する全便の停車パターンの和集合を、各停留所の最小 stop_sequence 順に並べて 0 から詰め直した値」です。同じグループ内でも便ごとに停車順・停車パターンが違う（枝分かれ・逆回り・区間便）場合、単一の直線的な順序ではその便の実際の停車順を表現できません。

GTFS 本来の stop_sequence はDBのどこにも保存されておらず（schedule_stop_times・daily_trip_stop_times・trip_stop_progress のいずれも stops.seq_order を引き継ぐだけ）、復元手段がありません。

実データでの例（10平日（四賀）_07時20分_系統241004）：便の停車順に並べた seq_order が 1, 5, 9, 12, 15, 18, 21, 24, 2, 6, 3, 7, 10, 13 … となり、ORDER BY seq_order は停車順とまったく別の並びを返します。

**発生条件**

同一 (route_id, direction_id, service_id) 内に停車パターンの異なる便が混在するとき。現在のダイヤで 948便中 185便（19.5%）が該当します。

**実際に起こりうる影響**

- dailyTripBuilder.js:234 が stopTimes[0] を始発とみなすため、72便で始発バス停・始発時刻が実際と異なる → その座標・時刻でGPSを探すので車両が永久に割り当たらない（未割当便）。
- finishService.getAssignmentTerminal() が ORDER BY seq_order DESC LIMIT 1 で終点を取るため、65便で終点判定が別のバス停になる → 終点到着を検知できない／途中で終了する。
- openAssignment() の lastValidSeq・originSeq が誤り、「通過」フラグが本来と違うバス停に付く。
- passStep1And3() の巻き戻り防止（currentMaxIdx）と探索範囲制限が破綻し、通過判定が進まない。
- predictArrivals() と /api/buses がシャッフルされた順序で停留所を返すため、利用者画面のバス停一覧と予想到着時刻の並びが実際の運行順と違う。

**修正案**

便ごとの順序を、路線共有の seq_order から切り離すのが本筋です。

- schedule_stop_times に stop_sequence INTEGER（GTFS原文の値、または便内0始まりの連番）を追加し、daily_trip_stop_times / trip_stop_progress / completed_trip_stop_times の seq_order はその便の中での 0..n-1 連番を入れる（stops.seq_order は表示順専用として残す）。
- 主キーは (daily_trip_id, seq_order) ／ (assignment_id, seq_order) へ寄せ、stop_id は属性にする（1便中に同一停留所を複数回通るケースにもそのまま対応できる）。
- 移行は seed → dailyTripBuilder → openAssignment の順に seq_order の意味を差し替えるだけで、判定ロジック本体（4つ先まで／後半80%除外／隣接区間）は式を変えずに正しく効くようになります。

**対応状況（✅ 対応済み）**

schedule_stop_times に stop_sequence INTEGER（便自身の中での0始まりの連番）を追加し、dailyTripBuilder の loadScheduleTrips() をはじめ順序を必要とする箇所はこちらを参照するように変更しました。daily_trip_stop_times / trip_stop_progress / completed_trip_stop_times / trip_arrival_predictions / trip_arrival_prediction_log の seq_order 列は、これまでどおり daily_trip_stop_times.seq_order を経由してそのまま流れてくる値ですが、その値自体が今回の修正で正しい便内連番になったため、これらのテーブル・主キー構造は変更していません（主キーを (daily_trip_id, seq_order) 等へ寄せる案は採らず、stop_id ベースのままとしています。理由は C-2 の対応状況を参照）。stops.seq_order は route_id・direction_id内の表示順専用に格下げしました。

実データ（948便）で検証した結果、seq_order の非単調化・欠番は解消し、全便で daily_trip_stop_times.seq_order が 0..n-1 の連番になることを確認しています。報告にあった具体例（10平日（四賀）_07時20分_系統241004）も、明科駅→神社裏→…→四賀支所という実際の停車順どおりに seq_order 0..19 が並ぶことを確認済みです。既存の segment_travel_stats・completed_trips 等の統計・履歴データは、stops.id の意味が変わるため引き継がず、migrate.js のマイグレーションで一度だけ空にしたうえで新しいデータ構造で再構築する方針としました。

### C-2 service_id をまたいで stops 行が別の物理バス停に上書きされ、座標と名称が入れ替わる

*DB整合性 / GTFS更新*

**該当箇所**
backend/src/db/seed.js:248-307（for (const { directionId, serviceId, trips } of directionServiceTrips) の中で seqOrder を 0 から振り直し、ON CONFLICT (route_id, direction_id, seq_order) DO UPDATE SET name, lat, lon … している箇所）

**問題の内容**

seqOrder は service_id グループごとに 0 から採番されるのに、UNIQUE 制約は (route_id, direction_id, seq_order) で service_id を含みません。そのため 平日グループが書いた stops 行を、土休日グループが同じ seq_order で UPDATE し、name / lat / lon を別のバス停の値へ書き換えます（行IDは維持されるため、平日便の schedule_stop_times は同じ行を参照したまま中身だけ別バス停になります）。どちらが残るかは trips.txt の並び順次第です。

**発生条件**

同一 (route_id, direction_id) に停車パターンの異なる service_id が存在するとき。現在のデータで 615 行（feed1: 83／feed2: 532）が別バス停に上書きされます。例：路線15 direction 0 の seq 0 が「信大病院玄関前（平日）」→「松本駅お城口（土休日）」。

**実際に起こりうる影響**

- 通過判定が別の場所の座標とGPSを突き合わせるため、到着を検知できない／まったく違う地点で到着扱いになる。
- /api/buses・時刻表・バス停検索が実在しない停車順・誤った停留所名を返す。
- segment_travel_stats が「別区間の所要時間」を同じキーに積む → ETA予測が恒常的にずれる。
- GTFS再取得（毎時）のたびに勝者が変わりうるため、運行中に停留所の座標がすり替わることがある。

README 10章に「同じ seq_order に別のバス停が入り込む余地が残っている／便起点方式では悪化しない」と記述がありますが、実際には停留所行そのものの実体が書き換わるため、便ごとの停車パターンでは救済されません。

**修正案**

C-1 と同じ変更で解消します。応急処置としては stops の UNIQUE を (route_id, direction_id, service_id, seq_order) にするか、GTFS の stop_id をそのまま持つ列を追加して (route_id, direction_id, gtfs_stop_id, occurrence) を一意キーにし、seq_order を単なる表示順にする方法があります。いずれもマイグレーションが必要なため、C-1 と同時に設計するのが安全です。

**対応状況（✅ 対応済み）**

修正案の後者（GTFS の stop_id + occurrence を一意キーにする方式）を採用しました。stops の UNIQUE 制約を (route_id, direction_id, gtfs_stop_id, occurrence) に変更し、service_id はキーに含めていません。service_id をキーに含める前者の案（応急処置）は、平日・土休日など複数の service_id グループが同じ物理バス停を共有できなくなり、day_type（曜日区分）が同じ複数の service_id にまたがる区間統計が本来1本にまとまるべきところで分裂してしまう副作用があるため見送りました。gtfs_stop_id + occurrence 方式であれば、occurrence が「その便自身の中で何回目にその物理停留所を通るか」という便に閉じた概念であるため、service_id グループが違っても同じ物理バス停・同じ通過回目は同じ stops 行を安全に共有でき、区間統計が無用に分裂しません。

実データで、同一 route_id・direction_id 内に複数の service_id グループが存在するケース（例: guruttomatsumotobus2:28 方向0、4つの service_id が同じ物理停留所群を共有）でも、(gtfs_stop_id, occurrence) が一致する行同士で名称・座標が食い違わないことを確認しています。マイグレーションでは、stops.id の意味が変わるため既存データは新しいキーへ移行せず、破棄したうえで seed() で作り直す方針としました（対応する migrate.js のステップは、コンテナ起動のたびに実行される都合上、一度だけ実行されるようガードしています）。

### C-3 通過判定の「4つ先まで」制限を seq_order の欠番が越えられず、便の進捗が始発で凍結する

*バス停通過判定 / 循環線*

**該当箇所**
backend/src/services/passDetection.js:161　`if (lastArrivedIdx !== -1 && stop.seq_order > lastArrivedIdx + 4) continue;`

**問題の内容**

循環線対策①の「直近到着バス停の4つ先まで」は停留所の個数を意図した制限ですが、実装は seq_order の数値差で判定しています。C-1 のとおり seq_order には欠番があるため、「次の停留所」の seq_order が 5 以上先にあるとその便は二度と候補に入らず、探索窓が永久に前進しません（窓は到着が確定したときにしか動かないため、自力で回復できません）。

**発生条件**

便の中で連続する2停留所の seq_order 差が 5 以上になるとき。feed2 の 360便中 54便（15%）が該当します（例：路線24 四賀線の seqs = [0, 5, 1, 4, 8, 11, …]）。

**実際に起こりうる影響**

該当便は始発バス停（割り当て時に到着済で登録される）から一歩も進まず、全バス停が「未到着」のまま。遅延は常に0分、ETAは時刻表そのまま、passInterpolate() も到着2件が揃わないため働かず、最終的に 割り当てから120分経過 で強制終了 → 担当車両不在 でクローズされます。利用者には「バスが始発から動いていない」ように見え続けます。

**修正案**

C-1 で seq_order を便内連番にすれば式は正しく機能します。それまでの暫定策としては、stopMaster の配列インデックスで距離を測る（currentIdx + 4）よう書き換えるだけでも凍結は解消します。lastArrivedIdx という変数名が実際には seq_order を保持している点も、同時に直すと誤解が減ります。

**対応状況（✅ 対応済み・passDetection.js自体は無修正）**

report記載のとおり、C-1（stops.seq_order を便内連番の schedule_stop_times.stop_sequence へ切り離す修正）だけで解消することを確認しました。passDetection.js の `stop.seq_order > lastArrivedIdx + 4` および H-3 の `stop.seq_order / totalStops > 0.8` は式を一切変更していません。修正後のデータでは trip_stop_progress.seq_order が便ごとに 0..n-1 の連番になるため、これらの式がそのまま正しく機能します。実データ（948便）で daily_trip_stop_times.seq_order が全便で 0..n-1 の連番になることを確認済みです。lastArrivedIdx のリネームは、判定ロジック本体の挙動に影響しない表面的な変更であり、今回は変更範囲を最小に保つため見送りました。

### C-4 プール上で BEGIN / COMMIT しているためトランザクションが成立せず、接続が open transaction のまま残る

*API / 管理画面 / 非同期処理*

**該当箇所**
backend/src/routes/api.js:190, 198, 203（PUT /api/admin/settings）

**問題の内容**

pool.query('BEGIN') → pool.query(INSERT …) → pool.query('COMMIT') と書かれていますが、pool.query() は毎回プールから別の接続を取り得ます。BEGIN を実行した接続と INSERT / COMMIT を実行する接続が一致する保証がありません。他のDBアクセス（同モジュール内の pool.query は全体で60箇所以上）はすべて同じプールを共有しています。

**発生条件**

この API を叩いたとき。プールに複数の空き接続がある（＝ほぼ常時）と成立します。

**実際に起こりうる影響**

- お知らせ更新がアトミックにならない（一部だけ反映されうる）。
- BEGIN を受けた接続がプールへ返却されると idle in transaction のまま滞留し、そのまま他のリクエストに再利用されると無関係な処理が同じトランザクションに巻き込まれる。COMMIT を受けた別接続では WARNING: there is no transaction in progress が出ます。
- 最悪、滞留した接続がロックを保持し続け、パイプライン側の更新がブロックされます（プールは max 10）。

**修正案**

他のサービス（touristSpots.replaceAllTouristSpots() など）と同様に const client = await pool.connect() を取り、client.query で BEGIN / INSERT / COMMIT / ROLLBACK を行い finally で release() する。設定5件のUPSERTなら単一の INSERT … VALUES (…),(…) ON CONFLICT 1文にまとめてトランザクション自体を不要にするのも手です。

**対応状況（✅ 対応済み）**

修正案の前者（`const client = await pool.connect()` を使う方式）を採用しました。backend/src/routes/api.js の `PUT /admin/settings` で、BEGIN／INSERT×5／COMMIT／ROLLBACK をすべて同一の `client` に対して実行し、`finally` で `client.release()` するように変更しました（既存の `touristSpots.replaceAllTouristSpots()` と同じパターン）。単一の `INSERT … VALUES (…),(…) ON CONFLICT` にまとめる案（修正案の後者）は、可変長のUPSERT文を都度組み立てる必要があり、可読性の面でメリットが薄いため見送りました。

実DB（docker composeのpostgres:16-alpine）に対して検証しました。25並列でこのAPIのロジックを同時実行しただけでは再現しなかったため、「全リクエストのBEGINを一斉発行 → 全リクエストのINSERTをカラムごとに一斉発行 → 全リクエストのCOMMITを一斉発行」という、プールの接続を意図的に奪い合わせる条件で再検証しました。修正前のコード（`pool.query('BEGIN')` 方式）ではこの条件で、最終的な5件の設定値が異なるリクエストの値の寄せ集めになり（例：`important_notice` はリクエスト7の値、`notice2` はリクエスト2の値、`notice1` に至っては今回の実行分ですらなく別の検証実行の値が残存）、アトミック性が失われることを実際に確認しました。修正後のコード（`pool.connect()` 方式）では同じ条件でも5件すべてが常に同一リクエストの値で揃うことを確認しています。あわせて `pg_stat_activity` で `idle in transaction` 状態の接続が処理前後とも0件であることも確認済みです（検証スクリプトはリポジトリには追加していません）。

### C-5 便のクローズと区間統計の集計が2本のタイマーから同時に走り、実績と統計が二重計上される

*非同期処理・競合 / 統計データ / DB整合性*

**該当箇所**
backend/src/services/finishService.js:136-190（closeDailyTrip）, 309-321 と backend/src/services/tripAssignment.js:341-458（reassignOrphanTrips）／ backend/src/services/etaPredictor.js:70-135（updateSegmentStats）／ backend/src/jobs/scheduler.js:19-46

**問題の内容**

scheduler.js はメインパイプラインと finish バッチを互いに独立した60秒タイマーで回し、それぞれ別のプール接続を使います。両者の多重実行防止フラグ（pipelineRunning / finishRunning）は自分の系統内でしか効きません。

closeDailyTrip() は finish 側（運行日を過ぎた便）とパイプライン側（reassignOrphanTrips）の両方から呼ばれます。同じ便が両条件を満たすことがあり、UPDATE daily_trips … WHERE closed_at IS NULL のガードは archiveAssignment() のあとに実行されるため、2つのトランザクションが同時に通ると completed_trips に重複行が入ります（一意制約もありません）。

updateSegmentStats() も同じ2系統から呼ばれ、SELECT … WHERE aggregated = FALSE … LIMIT 200 に FOR UPDATE SKIP LOCKED が無いため、同じ行を両方が読んで同じ実績を2回 avg_seconds に混ぜます。

**発生条件**

サーバー起動時に両タイマーが同時に開始されるため位相がほぼ揃っており、日付が変わった直後や再割り当てが発生した便で日常的に条件が揃います。

**実際に起こりうる影響**

運行実績CSVに同じ便が二重に出る／segment_travel_stats.sample_count と avg_seconds が歪む → ETA予測が実態から乖離する。統計は累積更新なので、一度汚染されると自然には戻りません。

**修正案**

- closeDailyTrip() の冒頭で SELECT … FROM daily_trips WHERE id = $1 AND closed_at IS NULL FOR UPDATE を取り、0行なら即リターンする。あわせて completed_trips に UNIQUE (daily_trip_id, assignment_id) を張る。
- updateSegmentStats() の SELECT を FOR UPDATE SKIP LOCKED にし、aggregated = TRUE の更新まで単一トランザクションに含める。
- あるいは finish バッチをパイプラインの一部（⑨番目のステップ）に統合し、タイマーを1本にする。

### H-1 終了エリア判定（終点から150m）が、循環線・往復線の途中で発火して便を打ち切る

*運行終了判定 / 循環線*

**該当箇所**
backend/src/services/finishService.js:252-259（条件②）、判定対象は getAssignmentTerminal() が返す最終停留所

**問題の内容**

条件②は「直近GPSが終点から END_AREA_RADIUS_METERS（150m）以内」だけを見ており、その便がどこまで進んでいるか（進捗）を一切参照しません。循環線・往復線では走行中に終点付近を通過するため、保護期間（既定10分）を過ぎた時点で誤発火します。松本市中心部はバス停が密集しているため、150m 圏内に入る機会が多くあります。

**発生条件**

始発から10分以降に終点から150m以内の地点を通る便。現在のダイヤで 199便（feed1: 50／feed2: 149）が該当。例：路線25 並柳団地線は「並柳団地口」が終点から141m にあり、18分の便の13分目に通過します。

**実際に起こりうる影響**

残り数停留所を残したまま担当割り当てが 終了エリア到達 で終了 → reassignOrphanTrips() はこの理由を「走り切った」とみなして再割り当てせずに便をクローズします。利用者画面から走行中のバスが消え、途中までの実績が is_official = TRUE でアーカイブされて区間統計に混ざります。

**修正案**

- 条件②に進捗の前提を足す：「終点の1つ手前の停留所が到着済」または「未到達バス停が終点のみ」のときだけ終了エリア判定を有効にする（条件④の救済判定と同じ考え方）。
- 加えて「終点の定刻の◯分前以降」という時間条件を併用すると、循環線の中間通過を確実に排除できます。
- 始発バス停と終点が同一・近接な便では条件②自体を無効化する選択肢もあります。

### H-2 GPSが3分途絶しただけで担当が終了し、便のリアルタイム表示が二度と復帰しない

*運行終了判定 / GPS取得*

**該当箇所**
backend/src/services/finishService.js:226-231（elapsedGpsMin >= 3 のハードコード）、:262-288（条件④）、tripAssignment.js:405-417（再割り当ての打ち切り）

**問題の内容**

「3分」は環境変数化されておらず、システム内の他のGPS鮮度しきい値と食い違っています：GPS_FRESHNESS_MIN = 15分（passDetection.js:280・locationFetcher.js:232）、ADMIN_STALE_GPS_MIN = 5分（管理画面アラート）、そして終了判定は3分。最も短いしきい値が最も重い処理（運行終了）に使われています。

さらに、条件④で終了した便は再割り当ての候補が居なければ 担当車両不在 でクローズされ、assignPendingTrips() は assignment_state = 'pending' の便しか見ないため、GPSが1分後に復旧しても復帰しません。

**発生条件**

位置情報フィードの配信遅延、トンネル・山間部（四賀線・奈川線・鹿教湯温泉線など）での測位途絶、事業者側のバッチ配信間隔が3分を超えたとき。パイプラインが60秒周期である以上、フィード側が2分間隔で配信するだけでも境界に触れます。

**実際に起こりうる影響**

山間路線を中心に、運行中のバスが利用者画面から突然消える。フィード全体が3分以上遅れた場合は全車両が一斉に inactive にされ、全便が一斉にクローズされます（UPDATE vehicles SET status='inactive' WHERE id = ANY(...) は車両単位のため、その車両が候補になっている他便の割り当ても巻き添えで終了します）。

**修正案**

- 3分を GPS_TIMEOUT_MIN のような環境変数にし、既定値を GPS_FRESHNESS_MIN と整合する値（8〜10分程度）へ引き上げる。
- 途絶を「終了」ではなく state = 'stalled' のような中間状態にし、GPSが戻ったら active へ復帰させる。少なくとも 担当車両不在 でのクローズは、途絶からさらに一定時間経ってから行う。
- フィード単位の一斉途絶（同一 feed_id の車両が全滅）を検知したら、個別車両の終了判定をスキップするサーキットブレーカを入れる。

### H-3 循環線対策②が「seq_order ÷ 便の停留所数」という異なる尺度の比を取っている

*バス停通過判定 / 循環線*

**該当箇所**
backend/src/services/passDetection.js:164　`stop.seq_order / totalStops > 0.8`（totalStops = stopMaster.length）

**問題の内容**

分子は路線共有の seq_order（欠番あり・便の停留所数より大きくなりうる）、分母はその便の停留所の個数です。C-1 のとおり両者の尺度が一致しないため、「便全体の後半80%」という意図と実際の除外範囲がずれます。例：路線24の20停留所の便では最大 seq_order が 58 で、比は最大 2.9 になり、実際には7番目あたりの停留所から先がすべて除外されます。

**発生条件**

seq_order に欠番のある便（948便中 255便で seq_order が 0..n-1 の連番になっていない）。始発から「時刻表所要時間の50%」の間だけ効きます。

**実際に起こりうる影響**

便の前半で正当な到着が検知されず、通過が飛ぶ。あとから passInterpolate() が線形補間で埋めるため実績時刻が推定値に置き換わり、その値が completed_trip_stop_times → segment_travel_stats まで流れて統計を鈍らせます。前半の遅延が検知できないぶん、ETAの初期値も甘くなります。

**修正案**

stopMaster 内の配列インデックス（i / totalStops）で比を取る。C-1 の修正で seq_order を便内連番にすれば現在の式のままで正しくなります。

### H-4 区間統計と直近ペース補正が「seq_order の差が1」を条件にしているため、統計が育たない路線がある

*統計データ / ETA予測*

**該当箇所**
backend/src/services/etaPredictor.js:99（updateSegmentStats）と :198（liveFactor の算出）　いずれも `if (to.seq_order - from.seq_order !== 1) continue;`

**問題の内容**

「隣接区間のみ統計対象にする」という意図に対し、実装は seq_order の数値差で隣接を判定しています。実際に隣り合う2停留所でも seq_order の差が2以上あれば統計にも、ペース補正にも一切使われません。

**発生条件**

seq_order に欠番のある便。実測では feed1 の 12.6%、feed2 の 31.0% の区間が対象外になります（路線24 四賀線などは大半が欠落）。

**実際に起こりうる影響**

- 対象外の区間では segment_travel_stats が何日走っても MIN_SAMPLES_FOR_TRUST = 3 に到達せず、ETAは恒久的に schedule_paced（時刻表所要時間 × ペース補正）止まりになります。README/CLAUDE.md が謳う「走り終える→統計が育つ→予測精度が上がる」ループが、これらの路線では回りません。
- liveFactor も算出できず常に 1 になるため、渋滞・悪天候時のペース補正がまったく効かない路線が生じます。
- 管理画面の予測精度監視では、この偏りが路線別の誤差としてしか見えず、原因が特定しづらくなります。

**修正案**

隣接判定を配列上の隣接（i と i+1 がその便の連続する停車）へ変更する。C-1 の修正で seq_order が便内連番になれば式のままで正しくなります。あわせて、既に蓄積済みの segment_travel_stats は seq_order の意味変更後に再構築が必要かどうかを確認してください（区間キーは stop_id なので基本的には流用できます）。

### H-5 GTFSファイル差し替え中に、時刻表検索・経路検索のインデックス構築が失敗しうる

*GTFS更新 / エラーハンドリング*

**該当箇所**
backend/src/services/gtfsFeedManager.js:162-193（既存ファイルを backup へ renameSync → 新ファイルを copyFileSync）

**問題の内容**

差し替えは「既存ファイルを退避 → 新ファイルを配置」の2段階で、その間フィードディレクトリに必須ファイルが存在しない時間帯が生まれます。gtfsTimetable.listFeedIds() はディレクトリの存在しか確認しないため、この窓でインデックス再構築（TTL30分切れ、または invalidateTimetableIndex() 直後の初回リクエスト）が走ると readCsv() が ENOENT で throw します。gtfsCalendar.readCsv() と gtfsFare も同じディレクトリを読みます。

**発生条件**

毎時のGTFS更新中（2フィード分の展開・コピー中）に、時刻表検索・経路検索・バス停検索のリクエストが来たとき。利用者アクセスのある時間帯なら日常的に起こりえます。

**実際に起こりうる影響**

時刻表検索・経路検索・バス停検索が 500 を返す。getIndex() の buildingPromise に失敗が乗ると、その回のリクエストが軒並み失敗します。管理画面のAPI稼働監視には 5xx として記録されますが、原因は「GTFS更新中」とは分かりません。

**修正案**

新しい展開先ディレクトリを別名で作り、ディレクトリごと1回の rename で切り替える（feedId.new → feedId）。あるいは差し替え中だけインデックス構築を待たせるフラグを持ち、待機中は既存のインデックスを返す。少なくとも readCsv の失敗をフィード単位で握って「そのフィードだけ前回のインデックスを保持」する形にすると、全体停止は避けられます。

### H-6 GTFSの内容が変わっていなくても毎時 seed() が全マスタを書き換え、trip_index のズレで便の同一性が失われる

*GTFS更新 / DB整合性*

**該当箇所**
backend/src/services/gtfsFeedManager.js:285-300（if (updated > 0) await seed()）、backend/src/db/seed.js:318-327, 444-491（ON CONFLICT (route_id, direction_id, service_id, trip_index) と全体1トランザクション）

**問題の内容**

ダウンロード成功＝内容変更とみなしており、ETag / Last-Modified / 内容ハッシュの比較がありません。そのため同じZIPでも毎時 seed() が走り、全 stops・全 schedule_stop_times を UPDATE します（stops は約2,000行、stop_times は数万行）。

trip_index は trips.txt 内での「そのグループ何番目か」という並び順に依存する値です。GTFS側で便が1本追加・削除されると以降の trip_index が全部ずれ、ON CONFLICT で既存行が別の便の内容に更新されます。daily_trips.schedule_trip_id と completed_trips.trip_id はこの行を参照したままです。

GTFSから消えた schedule_trips は削除されないため、古い便がDBに残り続けます。

seed() 全体が単一トランザクションで、ensureGtfsFilesPresent()（＝ネットワークダウンロード）もその中にあります。

**発生条件**

毎時のGTFS更新（無条件の再投入）。trip_index のズレはダイヤ改正時。

**実際に起こりうる影響**

ダイヤ改正の瞬間に、走行中の便の schedule_trip_id が別の便を指す → /api/buses の gtfs_trip_id が誤り、便詳細ページへのリンクが別の便に飛ぶ。運行実績の trip_id も後から意味が変わります。また、無条件再投入は毎時のDB負荷と長いトランザクション（＝運行処理のブロック）を生みます。

**修正案**

- ZIPの SHA-256 を feeds に記録し、変化があったときだけ展開・seed する（HTTPの If-None-Match / If-Modified-Since を併用できるとなお良い）。
- schedule_trips の一意キーを (route_id, gtfs_trip_id) へ移す。gtfs_trip_id は既に列があり、インデックスも張られています。trip_index は表示順専用に降格する。
- seed() のトランザクション境界をフィード単位に分け、ダウンロードはトランザクション外へ出す。

### H-7 バス停の「接近中のバス」が、定刻を過ぎた遅延便を一覧から落とす

*API / 遅延計算*

**該当箇所**
backend/src/services/busStopApproaching.js:36-39　`.filter((d) => d.seconds >= nowSeconds && d.seconds <= nowSeconds + APPROACH_WINDOW_SECONDS)`

**問題の内容**

候補となる便を時刻表上の定刻だけで絞っており、リアルタイムの遅延を考慮していません。遅延の反映は絞り込んだ後の並べ替え（built.sort()）でしか行われないため、定刻を1秒でも過ぎた便は候補集合から消えます。

**発生条件**

バスが遅れているとき。ADMIN_DELAY_ALERT_MIN = 5分 が「遅延」の運用しきい値なので、日常的に発生します。

**実際に起こりうる影響**

いちばん知りたい「遅れて向かっている次のバス」が消えるという、利用者にとって最も困る誤表示です。10分遅れのバスは定刻の瞬間に一覧から落ち、その後10分間「接近中のバスはありません」と表示され続けます。逆に、まだ来ていないのに一覧から消えるため「もう行ってしまった」と誤解させます。

**修正案**

下限側の窓を広げ、d.seconds >= nowSeconds - MAX_DELAY_LOOKBACK_SECONDS（例：20〜30分）で候補を拾ったうえで、リアルタイム突合の結果予測到着が現在時刻より前になった便だけを落とす。リアルタイムが取れない便は従来どおり定刻で判定する（soft-fail の方針は維持）。

**対応状況（✅ 対応済み）**

修正案のとおり実装しました。backend/src/services/busStopApproaching.js の候補ウィンドウの下限を `nowSeconds`（現在時刻）から `nowSeconds - MAX_DELAY_LOOKBACK_SECONDS`（30分）へ広げ、リアルタイム突合後に「予測到着（定刻＋遅延分）が現在時刻より前になった便」だけを一覧から落とすようにしました（`isWithinApproachWindow()` / `computeEtaSeconds()` として切り出し）。リアルタイムが取れない便は従来どおり定刻で判定します（soft-fail方針の維持）。

10分遅れのバスが定刻を過ぎた瞬間に一覧から消えず、実際に到着したと判定されるまで表示され続けることを `backend/test/busStopApproaching.test.js` の単体テストで確認しました。あわせて実際のGTFSデータ（松本駅お城口）に対して `getApproachingBuses()` を実行し、既存のリアルタイム無し・soft-fail経路も含めて例外なく動作することをスモークテストで確認しています。

### H-8 運行日カレンダーの日付・曜日算出がサーバのローカルタイムゾーンに依存している

*当日便生成 / API*

**該当箇所**

**対応状況（✅ 対応済み）**

Dockerfile / docker-compose.yml への `ENV TZ=Asia/Tokyo` 設定、PostgreSQL側の `TimeZone` 設定（M-1 の対応）は今回のスコープ（C-4・H-7・H-8）には含めていないため未実施です。

### M-1 CURRENT_DATE がDBサーバのタイムゾーンで評価され、便のクローズと掃除が最大9時間遅れる

### M-6 GPS時刻の「未来」判定と日時書式が、時計ずれ・書式変更に弱い

**該当箇所**

### L-11 パイプラインが間隔内に終わらなかったことを検知・記録していない

*非同期処理 / 管理画面*

**該当箇所**
backend/src/jobs/scheduler.js:19-27（if (pipelineRunning) return; で黙ってスキップ）

**問題の内容**

多重実行防止は正しい設計ですが、スキップした事実がどこにも残りません。jobMonitor は各ステップの所要時間を記録していますが、「何周期スキップしたか」は分かりません。

**発生条件**

1周期の処理が POLL_INTERVAL_SECONDS を超えたとき（M-10・M-8・H-6 が重なるとありえます）。

**実際に起こりうる影響**

実質的なポーリング間隔が2分・3分へ伸びていても気づけません。GPSの鮮度判定（3分・15分）はこの間隔を前提にしているため、H-2 の誤終了が増える方向に効きます。

**修正案**

スキップ回数を jobMonitor にカウンタとして持たせ、/api/admin/job-monitor と管理画面のジョブ監視に表示する。連続スキップが閾値を超えたらアラート化する。

### L-12 ETAの遅延キャップが、実際に大きく遅れている便の到着を早く見せる

*ETA予測*

**該当箇所**
backend/src/services/etaPredictor.js:45-66（resolveDelayCeiling() / capPredictedDelay()）

**問題の内容**

暴走防止という意図は妥当ですが、上限は現在の遅れだけで決まり、残り区間の長さや実際の統計を参照しません。現在1分遅れなら以降どのバス停でも上限5分、2分遅れなら7分です。さらに DELAY_RECOVERY_BOOST = 1.15 は遅れ解消方向の予測を常に1.15倍強調します。

**発生条件**

序盤は定時に近かったが、途中の渋滞区間で大きく遅れる便（松本駅周辺・国道19号など）。

**実際に起こりうる影響**

終盤のバス停で「あと5分」と出ているバスが15分後に来る、という過小予測に偏ります。利用者はバス停で待ち続けることになり、遅延そのものより体感の悪化が大きくなります。管理画面の予測精度監視で meanErrorMinutes がプラス側に偏っていれば、この仮説を確認できます。

**修正案**

まず /api/admin/prediction-accuracy の誤差バイアス（符号付き平均）を路線・リードタイム別に確認し、偏りが確認できたら上限を「残り所要時間に比例した値」へ変える。DELAY_RECOVERY_BOOST は 1.0 に戻して検証してから調整するのが安全です。この所見は仮説であり、実測で検証してから手を入れてください。
