# バス運行システム点検所見

GPS取得から当日便生成・車両割り当て・通過判定・遅延計算・ETA予測・統計・API・管理画面までを通しで読み、コード上の欠陥に加えて「コードは動くが実運用で誤判定しうる箇所」を洗い出しました。判定ロジックに関わる所見は、実際に配信されている2フィードのGTFSデータ（計948便）に対して影響件数を実測しています。コードは一切変更していません。

- **対象**: bussystem @ 0c23091
- **照合した仕様**: CLAUDE.md / README.md / docs/
- **所見数**: 41件
- **検証データ**: data gtfs/（948便）

> **追記（対応状況）**: Critical の5件（C-1〜C-5）はすべて対応済みです。stops を物理バス停（gtfs_stop_id）＋通過回数（occurrence）で一意化し、便ごとの実際の停車順は schedule_stop_times に新設した stop_sequence で持つ設計へ変更しました。同じ根から出ていた H-3・H-4 もコード変更なしで解消しています。C-4（プール上のBEGIN/COMMIT）は `client = await pool.connect()` による単一接続への固定で解消しました。C-5（便クローズと統計集計の二重実行レース）は、closeDailyTrip() の行ロック・completed_trips への UNIQUE 制約・updateSegmentStats() の FOR UPDATE SKIP LOCKED 化で解消しました。High のうち H-7（接近中バス一覧が遅延便を落とす）・H-8（運行日判定のTZ依存）も対応済みです。既存の segment_travel_stats・completed_trips 等の統計・履歴データは引き継がず、マイグレーションで一度だけ空にして作り直す方針を採りました（C-5対応時に実データで見つかった completed_trips の重複も、同じ方針でマイグレーションが自動的に解消します）。詳細は各所見の「対応状況」欄、および[03 Critical](#03-critical)・[04 High](#04-high)・[07 着手順の提案](#07-着手順の提案)を参照してください。C-5以外の所見（High の一部・Medium・Low）は本追記時点で未対応です。

## 03 Critical

利用者に誤った運行情報が表示される、またはマスタデータが壊れるもの。

### C-1 便の停車順を表す seq_order が非単調・欠番になり、順序に依存する全処理が崩れる ✅対応済み

*DB整合性 / 当日便生成 / 循環線*

**問題**：`stops.seq_order`は路線内の全便の停車パターンの和集合を詰め直した値で、便ごとに停車パターンが異なる場合（枝分かれ・逆回り・区間便）は実際の停車順を表現できない。GTFS本来の`stop_sequence`はDBに保存されておらず復元手段もなかった（948便中185便＝19.5%で発生）。始発・終点判定の誤りによる未割当便・誤終了、通過判定の停止、予測到着順の乱れなど広範囲に影響していた。

**対応**：`schedule_stop_times`に`stop_sequence`（便内0始まりの連番）を追加し、順序を必要とする箇所（`dailyTripBuilder.js`の`loadScheduleTrips()`ほか）はこちらを参照するよう変更した。`daily_trip_stop_times`以降の`seq_order`列はこの値をそのまま引き継ぐため、テーブル・主キー構造自体は変更していない（stop_idベースを維持した理由はC-2を参照）。`stops.seq_order`は表示順専用に格下げした。既存の`segment_travel_stats`・`completed_trips`等の統計・履歴データは`stops.id`の意味が変わるため引き継がず、マイグレーションで一度だけ空にして新しいデータ構造で再構築する方針を採った。実データ（948便）で全便のseq_orderが0..n-1の連番になることを確認済み。

### C-2 service_id をまたいで stops 行が別の物理バス停に上書きされ、座標と名称が入れ替わる ✅対応済み

*DB整合性 / GTFS更新*

**問題**：`stops`のUNIQUE制約が`(route_id, direction_id, seq_order)`でservice_idを含まないため、seq_orderがservice_idグループごとに0から振り直される都合上、平日グループが書いた行を土休日グループが同じseq_orderでUPDATEし、`name`/`lat`/`lon`が別バス停の値へ入れ替わっていた（615行が該当。どちらが残るかはtrips.txtの並び順次第）。通過判定の座標ズレ、ETA統計の汚染、GTFS再取得のたびに座標がすり替わる、といった影響があった。

**対応**：`stops`のUNIQUE制約を`(route_id, direction_id, gtfs_stop_id, occurrence)`に変更した（`occurrence`＝便自身の中でその物理停留所を何回目に通るか）。service_idをキーに含める案（応急処置）は、平日・土休日など複数のservice_idグループが同じ物理バス停を共有できなくなり、day_typeが同じ区間統計が分裂する副作用があるため見送った。既存データはC-1と同じくstops.idの意味が変わるため引き継がず、seed()で作り直す。

### C-3 通過判定の「4つ先まで」制限を seq_order の欠番が越えられず、便の進捗が始発で凍結する ✅対応済み（C-1修正の副次効果）

*バス停通過判定 / 循環線*

**問題**：循環線対策①「直近到着バス停の4つ先まで」（`passDetection.js`の`stop.seq_order > lastArrivedIdx + 4`）は停留所の個数を意図した制限だが、seq_orderの数値差で判定しているため、seq_orderの欠番により「次の停留所」が5以上先だと便が二度と候補に入らず進捗が凍結していた（feed2の360便中54便＝15%が該当）。該当便は全バス停が「未到着」のまま120分で強制終了していた。

**対応**：`passDetection.js`のコードは無修正。C-1でseq_orderが便内連番になったことでこの式がそのまま正しく機能するようになった。

### C-4 プール上で BEGIN / COMMIT しているためトランザクションが成立せず、接続が open transaction のまま残る ✅対応済み

*API / 管理画面 / 非同期処理*

**問題**：`PUT /api/admin/settings`が`pool.query('BEGIN')`→`INSERT`→`pool.query('COMMIT')`という書き方で、`pool.query()`は毎回別接続を取りうるためアトミック性が保証されず、`idle in transaction`のまま接続が滞留する恐れがあった。

**対応**：`const client = await pool.connect()`で単一接続に固定し、`finally`で`release()`する方式に変更した（既存の`touristSpots.replaceAllTouristSpots()`と同じパターン）。プールの接続を意図的に奪い合わせる条件で検証し、修正前は5件の設定値が異なるリクエストの値の寄せ集めになること、修正後は常に単一リクエストの値で揃うことを確認した。

### C-5 便のクローズと区間統計の集計が2本のタイマーから同時に走り、実績と統計が二重計上される ✅対応済み

*非同期処理・競合 / 統計データ / DB整合性*

**問題**：メインパイプラインと運行終了バッチ（`finishService.js`）は独立した2本のタイマーで動き、`closeDailyTrip()`・`updateSegmentStats()`はどちらの系統からも呼ばれうる（前者は`reassignOrphanTrips()`から、後者は運行日終了の掃除から）。サーバー起動時に両タイマーがほぼ同時に開始されるため位相が揃いやすく、日付が変わった直後や再割り当てが発生した便で、同じ便を両方が同時に処理する条件が日常的に揃っていた。結果として`completed_trips`への実績二重アーカイブ、`segment_travel_stats`の二重集計（`sample_count`・`avg_seconds`の歪み→ETA予測の乖離）が起きていた。対応前の検証環境で実際に6組・12行の重複が見つかっている（`is_official=TRUE`かつ`aggregated=TRUE`、`finished_at`の差は数百ミリ秒程度）。

**対応**：

- `closeDailyTrip()`冒頭で`SELECT id FROM daily_trips WHERE id = $1 AND closed_at IS NULL FOR UPDATE`による行ロックを取り、0行（＝既に他方が処理済み）なら即`{ archived: 0 }`で抜けるようにした。後発側は先発側のCOMMITまでブロックされたあと`closed_at`が埋まっていることを確認して抜けるため、二重アーカイブが構造的に起きなくなる。
- `completed_trips`に`UNIQUE (daily_trip_id, assignment_id)`を安全網として追加した（行ロックが一次防御、制約は「万一ロックをすり抜けるコード変更が将来入っても実績が黙って二重に入ることだけは防ぐ」ための二次防御）。
- `updateSegmentStats()`を`BEGIN`〜`COMMIT`の単一トランザクションにまとめ、対象行の取得を`SELECT … FOR UPDATE SKIP LOCKED`にした。`segment_travel_stats`への反映も、JS側でread-modify-writeしていたのをやめ、`INSERT … ON CONFLICT (from_stop_id, to_stop_id, day_type, hour_bucket) DO UPDATE`の原子的な1文に置き換えた。`aggregated = TRUE`への更新も同じトランザクションに含めている。

移行時のマイグレーション（`migrate.js`）で、見つかった重複行を`(daily_trip_id, assignment_id)`ごとに最小idだけ残して削除し、`segment_travel_stats`をTRUNCATE・`completed_trips.aggregated`を全行FALSEに戻して`updateSegmentStats()`に作り直させたうえで、UNIQUE制約を追加している。このステップは「制約がまだ存在しない」ことをガードにしており、2回目以降の起動ではスキップされる。finishバッチをパイプラインへ統合しタイマーを1本にする案は、finishTrips()が独自の保護期間・終了条件判定を持つ設計自体は妥当なため見送った。

## 04 High

特定条件で運行判定が確実に誤るもの。多くは「コードは動くが実際のバス運行では誤判定する」類型です。

### H-1 終了エリア判定（終点から150m）が、循環線・往復線の途中で発火して便を打ち切る

*運行終了判定 / 循環線*

**該当箇所**
backend/src/services/finishService.js:252-259（条件②）、判定対象は getAssignmentTerminal() が返す最終停留所

**問題の内容**

条件②は「直近GPSが終点から END_AREA_RADIUS_METERS（150m）以内」だけを見ており、その便がどこまで進んでいるか（進捗）を一切参照しません。循環線・往復線では走行中に終点付近を通過するため、保護期間（既定10分）を過ぎた時点で誤発火します。松本市中心部はバス停が密集しているため、150m 圏内に入る機会が多くあります。

**発生条件**

始発から10分以降に終点から150m以内の地点を通る便。現在のダイヤで 199便（feed1: 50／feed2: 149）が該当。例：路線25 並柳団地線は「並柳団地口」が終点から141m にあり、18分の便の13分目に通過します。

**実際に起こりうる影響**

残り数停留所を残したまま担当割り当てが 終了エリア到達 で終了 → reassignOrphanTrips() はこの理由を「走り切った」とみなして再割り当てせずに便をクローズします。利用者画面から走行中のバスが消え、途中までの実績が is_official = TRUE でアーカイブされて区間統計に混ざります。

**修正案**

- 条件②に進捗の前提を足す：「終点の1つ手前の停留所が到着済」または「未到達バス停が終点のみ」のときだけ終了エリア判定を有効にする（条件④の救済判定と同じ考え方）。
- 加えて「終点の定刻の◯分前以降」という時間条件を併用すると、循環線の中間通過を確実に排除できます。
- 始発バス停と終点が同一・近接な便では条件②自体を無効化する選択肢もあります。

**対応状況**: 条件②（終了エリア到達）自体を撤去しました。`END_AREA_RADIUS_METERS`設定・関連コード（`finishService.js`の条件②評価、`SUCCESS_END_REASONS`・`reassignOrphanTrips()`の`終了エリア到達`判定）もあわせて削除済みです。運行終了は条件①（終点到着済み）・条件③（一定時間経過）・条件④（GPS途絶、終点到着救済判定含む）のみで判定します。

### H-2 GPSが3分途絶しただけで担当が終了し、便のリアルタイム表示が二度と復帰しない

*運行終了判定 / GPS取得*

**該当箇所**
backend/src/services/finishService.js:226-231（elapsedGpsMin >= 3 のハードコード）、:262-288（条件④）、tripAssignment.js:405-417（再割り当ての打ち切り）

**問題の内容**

「3分」は環境変数化されておらず、システム内の他のGPS鮮度しきい値と食い違っています：GPS_FRESHNESS_MIN = 15分（passDetection.js:280・locationFetcher.js:232）、ADMIN_STALE_GPS_MIN = 5分（管理画面アラート）、そして終了判定は3分。最も短いしきい値が最も重い処理（運行終了）に使われています。

さらに、条件④で終了した便は再割り当ての候補が居なければ 担当車両不在 でクローズされ、assignPendingTrips() は assignment_state = 'pending' の便しか見ないため、GPSが1分後に復旧しても復帰しません。

**発生条件**

位置情報フィードの配信遅延、トンネル・山間部（四賀線・奈川線・鹿教湯温泉線など）での測位途絶、事業者側のバッチ配信間隔が3分を超えたとき。パイプラインが60秒周期である以上、フィード側が2分間隔で配信するだけでも境界に触れます。

**実際に起こりうる影響**

山間路線を中心に、運行中のバスが利用者画面から突然消える。フィード全体が3分以上遅れた場合は全車両が一斉に inactive にされ、全便が一斉にクローズされます（UPDATE vehicles SET status='inactive' WHERE id = ANY(...) は車両単位のため、その車両が候補になっている他便の割り当ても巻き添えで終了します）。

**修正案**

- 3分を GPS_TIMEOUT_MIN のような環境変数にし、既定値を GPS_FRESHNESS_MIN と整合する値（8〜10分程度）へ引き上げる。
- 途絶を「終了」ではなく state = 'stalled' のような中間状態にし、GPSが戻ったら active へ復帰させる。少なくとも 担当車両不在 でのクローズは、途絶からさらに一定時間経ってから行う。
- フィード単位の一斉途絶（同一 feed_id の車両が全滅）を検知したら、個別車両の終了判定をスキップするサーキットブレーカを入れる。

### H-3 循環線対策②が「seq_order ÷ 便の停留所数」という異なる尺度の比を取っている ✅対応済み（C-1修正の副次効果）

*バス停通過判定 / 循環線*

**問題**：`stop.seq_order / totalStops > 0.8`（循環線対策②）は分子（路線共有のseq_order、欠番あり）と分母（便の停留所数）の尺度が一致せず、「便全体の後半80%」という意図と実際の除外範囲がずれていた。便の前半で正当な到着が検知されず、線形補間の推定値が統計まで流れて精度を鈍らせる影響があった。

**対応**：コードは無修正。C-1でseq_orderが便内連番になったことでこの式がそのまま正しく機能するようになった。

### H-4 区間統計と直近ペース補正が「seq_order の差が1」を条件にしているため、統計が育たない路線がある ✅対応済み（C-1修正の副次効果）

### H-5 GTFSファイル差し替え中に、時刻表検索・経路検索のインデックス構築が失敗しうる

*GTFS更新 / エラーハンドリング*

**該当箇所**
backend/src/services/gtfsFeedManager.js:162-193（既存ファイルを backup へ renameSync → 新ファイルを copyFileSync）

**問題の内容**

差し替えは「既存ファイルを退避 → 新ファイルを配置」の2段階で、その間フィードディレクトリに必須ファイルが存在しない時間帯が生まれます。gtfsTimetable.listFeedIds() はディレクトリの存在しか確認しないため、この窓でインデックス再構築（TTL30分切れ、または invalidateTimetableIndex() 直後の初回リクエスト）が走ると readCsv() が ENOENT で throw します。gtfsCalendar.readCsv() と gtfsFare も同じディレクトリを読みます。

**発生条件**

毎時のGTFS更新中（2フィード分の展開・コピー中）に、時刻表検索・経路検索・バス停検索のリクエストが来たとき。利用者アクセスのある時間帯なら日常的に起こりえます。

**実際に起こりうる影響**

時刻表検索・経路検索・バス停検索が 500 を返す。getIndex() の buildingPromise に失敗が乗ると、その回のリクエストが軒並み失敗します。管理画面のAPI稼働監視には 5xx として記録されますが、原因は「GTFS更新中」とは分かりません。

**修正案**

新しい展開先ディレクトリを別名で作り、ディレクトリごと1回の rename で切り替える（feedId.new → feedId）。あるいは差し替え中だけインデックス構築を待たせるフラグを持ち、待機中は既存のインデックスを返す。少なくとも readCsv の失敗をフィード単位で握って「そのフィードだけ前回のインデックスを保持」する形にすると、全体停止は避けられます。

### H-6 GTFSの内容が変わっていなくても毎時 seed() が全マスタを書き換え、trip_index のズレで便の同一性が失われる

*GTFS更新 / DB整合性*

**該当箇所**
backend/src/services/gtfsFeedManager.js:285-300（if (updated > 0) await seed()）、backend/src/db/seed.js:318-327, 444-491（ON CONFLICT (route_id, direction_id, service_id, trip_index) と全体1トランザクション）

**問題の内容**

ダウンロード成功＝内容変更とみなしており、ETag / Last-Modified / 内容ハッシュの比較がありません。そのため同じZIPでも毎時 seed() が走り、全 stops・全 schedule_stop_times を UPDATE します（stops は約2,000行、stop_times は数万行）。

trip_index は trips.txt 内での「そのグループ何番目か」という並び順に依存する値です。GTFS側で便が1本追加・削除されると以降の trip_index が全部ずれ、ON CONFLICT で既存行が別の便の内容に更新されます。daily_trips.schedule_trip_id と completed_trips.trip_id はこの行を参照したままです。

GTFSから消えた schedule_trips は削除されないため、古い便がDBに残り続けます。

seed() 全体が単一トランザクションで、ensureGtfsFilesPresent()（＝ネットワークダウンロード）もその中にあります。

**発生条件**

毎時のGTFS更新（無条件の再投入）。trip_index のズレはダイヤ改正時。

**実際に起こりうる影響**

ダイヤ改正の瞬間に、走行中の便の schedule_trip_id が別の便を指す → /api/buses の gtfs_trip_id が誤り、便詳細ページへのリンクが別の便に飛ぶ。運行実績の trip_id も後から意味が変わります。また、無条件再投入は毎時のDB負荷と長いトランザクション（＝運行処理のブロック）を生みます。

**修正案**

- ZIPの SHA-256 を feeds に記録し、変化があったときだけ展開・seed する（HTTPの If-None-Match / If-Modified-Since を併用できるとなお良い）。
- schedule_trips の一意キーを (route_id, gtfs_trip_id) へ移す。gtfs_trip_id は既に列があり、インデックスも張られています。trip_index は表示順専用に降格する。
- seed() のトランザクション境界をフィード単位に分け、ダウンロードはトランザクション外へ出す。

### H-7 バス停の「接近中のバス」が、定刻を過ぎた遅延便を一覧から落とす ✅対応済み

*API / 遅延計算*

**問題**：`busStopApproaching.js`の候補ウィンドウが時刻表上の定刻だけで絞られており、遅延の反映は絞り込み後の並べ替えでしか行われないため、定刻を1秒でも過ぎた便は候補集合から消えていた。10分遅れのバスは定刻の瞬間に一覧から落ち、その後10分間「接近中のバスはありません」と表示され続けるという、利用者にとって最も困る誤表示だった。

**対応**：候補ウィンドウの下限を`nowSeconds`（現在時刻）から`nowSeconds - MAX_DELAY_LOOKBACK_SECONDS`（30分）へ広げ、リアルタイム突合後に「予測到着（定刻＋遅延分）が現在時刻より前になった便」だけを一覧から落とすようにした（`isWithinApproachWindow()`/`computeEtaSeconds()`）。リアルタイムが取れない便は従来どおり定刻で判定する（soft-fail方針は維持）。

### H-8 運行日カレンダーの日付・曜日算出がサーバのローカルタイムゾーンに依存している ✅対応済み

*当日便生成 / API*

**問題**：コンテナはUTCで動くが、`gtfsCalendar.js`の`getDayOfWeek()`/`formatDate()`だけがJST固定のIntlを使わずローカル系メソッド（`getDay()`等）で日付・曜日を出していた。UTC環境でJST 0:00〜9:00に当日便が未生成の状態で`/api/timetable`が呼ばれると、前日の曜日のダイヤが「本日の時刻表」として表示される恐れがあった（始発5:40と時間帯が重なる）。

### M-1 CURRENT_DATE がDBサーバのタイムゾーンで評価され、便のクローズと掃除が最大9時間遅れる

*DB整合性 / 運行終了判定*

**該当箇所**

**問題の内容**

service_date は JST 基準（getServiceDateString()）で書き込まれるのに、比較対象の CURRENT_DATE はDBセッションのタイムゾーン（postgres:16-alpine の既定 = UTC）で評価されます。

**発生条件**

### M-6 GPS時刻の「未来」判定と日時書式が、時計ずれ・書式変更に弱い

*GPS取得*

**該当箇所**
backend/src/services/locationFetcher.js:146-150, 242-243

**問題の内容**

gpsDate > now の now は fetchLocation() の冒頭で1度だけ取得され、3フィードの取得（各最大30秒）中ずっと固定です。処理が進むほど now は過去になり、正常なデータが「未来」として捨てられます。事業者側の時計が数秒進んでいるだけでも同じことが起きます。

日時のパースが new Date(str.replace(/-/g,'/') + ' +0900') という書式依存の実装です。フィードが ISO 8601（2026-08-18T10:00:00）に変わると 2026/08/18T10:00:00 +0900 となり全行が NaN → 全件破棄されます。

**発生条件**

事業者側の時計ずれ、フィードの応答が遅いとき、配信書式の変更時。

**実際に起こりうる影響**

**修正案**

ループ内で Date.now() を取り直し、さらに gpsDate > now + 許容ずれ（例60秒） のときだけ破棄する。パースは正規表現で YYYY[-/]MM[-/]DD[ T]HH:mm(:ss)? を抽出して Date.UTC(...) - 9h で組み立てる形にし、失敗率が閾値を超えたら last_status = 'error' にして管理画面へ出す。

途中終了自体はDB側でロールバックされますが、gtfsFeedManager のファイル差し替え中（H-5）に落ちるとフィードディレクトリが不完全なまま残ります（ensureGtfsFilesPresent() が次回起動で復旧するため実害は限定的）。

**修正案**

SIGTERM / SIGINT の両方で、タイマー停止 → HTTPサーバーの close() → pool.end() の順に待ってから終了する。猶予タイマー（例10秒）で強制終了のフォールバックも入れてください。

### L-6 位置情報CSVのパーサがエスケープされたダブルクォートに対応していない

*GPS取得*

**該当箇所**
backend/src/services/locationFetcher.js:15-33（utils/csv.js:20-25 や seed.js:19-23 は "" を処理しているが、ここだけ未対応）

**問題の内容**

同じ処理のパーサがリポジトリ内に4つあり、locationFetcher のものだけ ""（エスケープされた引用符）を扱えず、また BOM 除去もありません。

**発生条件**

CSVのフィールドに引用符が含まれるとき。

**実際に起こりうる影響**

列がずれ、緯度経度が NaN になって skippedInvalidLatLon として静かに捨てられます。

**修正案**

utils/csv.js の parseCsvLine を再利用する（同モジュールは parseCsv がヘッダ行を前提にしているため、行パーサだけを取り込む形で十分です）。

### L-7 観光スポットの一括洗い替えで enabled が復帰しない

*管理画面*

**該当箇所**
backend/src/services/touristSpots.js:210-226（ON CONFLICT (name) DO UPDATE の SET 句に enabled が無い）

**問題の内容**

一括テキストは「全件洗い替え」の位置づけですが、既存行の enabled は更新されません。UIで無効化したスポットを再投入しても無効のままです。

**発生条件**

無効化したスポットを含むテキストを再投入したとき。

**実際に起こりうる影響**

「テキストに書いたのに公開されない」という原因の分かりにくい挙動。逆に、意図的な無効化を保持したい仕様なら現状で正しいので、どちらの仕様かを決める必要があります（docs/観光スポット情報_仕様書.md に記述がありません）。

**修正案**

仕様を決めたうえで、洗い替えなら enabled = TRUE を SET 句に足す。保持が正なら仕様書と管理画面に明記する。

### L-8 負荷チェックのポーリング自体が閲覧数を押し上げ続ける

*管理画面 / API*

**該当箇所**
frontend/app.js:1094-1095（setInterval(checkServerLoad, POLL_MS)）と backend/src/routes/api.js:53-59（X-Client-Id 付きリクエストを全部カウント）

**問題の内容**

/api/server-load は自動更新がOFFでも、どの画面でも20秒ごとに呼ばれ、X-Client-Id が付くため閲覧数としてカウントされます。つまり負荷判定のための通信が負荷指標を作っています。タブを開きっぱなしにしているだけの利用者も「アクティブ」に数えられます。

**発生条件**

常時。

**実際に起こりうる影響**

HIGH_LOAD_VIEWER_THRESHOLD（既定50）に実態より早く到達し、必要のない自動更新の一時停止が起きます。管理画面の閲覧数も実際の利用者数より多めに出ます。

**修正案**

/api/server-load をカウント対象から除外する（ミドルウェアでパスを除く）。あわせて document.visibilityState !== 'visible' のときはポーリングを止めると、指標が実態に近づきます。

### L-9 有効なGTFSフィードが0件のとき、更新間隔の記録が更新されない

*GTFS更新*

**該当箇所**
backend/src/services/gtfsFeedManager.js:261-265（if (feeds.length === 0) return が lastGtfsUpdateAt = now より前にある）

**問題の内容**

早期リターンで lastGtfsUpdateAt が更新されないため、次の周期でも間隔チェックを素通りします。

**発生条件**

全GTFSフィードを enabled: false にしたとき。

**実際に起こりうる影響**

60秒ごとに接続を取得してログを出すだけの無駄な処理が回ります（実害は軽微）。

**修正案**

lastGtfsUpdateAt = now を finally か関数の入口側に移す。

### L-10 data gtfs/ が永続ボリュームでなく、再作成のたびに全フィードを再取得する

*GTFS更新*

**該当箇所**
Dockerfile:17（COPY ["data gtfs", "data gtfs"]）、docker-compose.yml の backend サービスに volumes 指定なし

**問題の内容**

ダウンロードしたGTFSはコンテナのレイヤ上にのみ残ります。コンテナ再作成でイメージ内の古いGTFSに巻き戻り、ensureGtfsFilesPresent() はファイルが揃っているかしか見ないので再取得も走りません（次の毎時更新まで古いままです）。

**発生条件**

コンテナの再作成・再デプロイ時。

**実際に起こりうる影響**

デプロイ直後、最大1時間ダイヤ改正前のGTFSで当日便が生成されます。イメージ内のGTFSが十分古ければ運行日カレンダーの期間外になり、当日便が0件になる可能性もあります（M-2 により期間チェックが無いので現状は生成されますが、便自体が古いダイヤになります）。

**修正案**

docker-compose.yml の backend に名前付きボリュームを割り当てる（gtfs_data:/app/data gtfs）。または起動時に必ず1回 updateAllGtfsFeeds() を強制実行する（lastGtfsUpdateAt の初期値が0なので現状も初回は走ります。この点を明示的な仕様としてコメント化してください）。

### L-11 パイプラインが間隔内に終わらなかったことを検知・記録していない

*非同期処理 / 管理画面*

**該当箇所**
backend/src/jobs/scheduler.js:19-27（if (pipelineRunning) return; で黙ってスキップ）

**問題の内容**

多重実行防止は正しい設計ですが、スキップした事実がどこにも残りません。jobMonitor は各ステップの所要時間を記録していますが、「何周期スキップしたか」は分かりません。

**発生条件**

1周期の処理が POLL_INTERVAL_SECONDS を超えたとき（M-10・M-8・H-6 が重なるとありえます）。

**実際に起こりうる影響**

実質的なポーリング間隔が2分・3分へ伸びていても気づけません。GPSの鮮度判定（3分・15分）はこの間隔を前提にしているため、H-2 の誤終了が増える方向に効きます。

**修正案**

スキップ回数を jobMonitor にカウンタとして持たせ、/api/admin/job-monitor と管理画面のジョブ監視に表示する。連続スキップが閾値を超えたらアラート化する。

### L-12 ETAの遅延キャップが、実際に大きく遅れている便の到着を早く見せる

*ETA予測*

**該当箇所**
backend/src/services/etaPredictor.js:45-66（resolveDelayCeiling() / capPredictedDelay()）

**問題の内容**

暴走防止という意図は妥当ですが、上限は現在の遅れだけで決まり、残り区間の長さや実際の統計を参照しません。現在1分遅れなら以降どのバス停でも上限5分、2分遅れなら7分です。さらに DELAY_RECOVERY_BOOST = 1.15 は遅れ解消方向の予測を常に1.15倍強調します。

**発生条件**

序盤は定時に近かったが、途中の渋滞区間で大きく遅れる便（松本駅周辺・国道19号など）。

**実際に起こりうる影響**

終盤のバス停で「あと5分」と出ているバスが15分後に来る、という過小予測に偏ります。利用者はバス停で待ち続けることになり、遅延そのものより体感の悪化が大きくなります。管理画面の予測精度監視で meanErrorMinutes がプラス側に偏っていれば、この仮説を確認できます。

**修正案**

まず /api/admin/prediction-accuracy の誤差バイアス（符号付き平均）を路線・リードタイム別に確認し、偏りが確認できたら上限を「残り所要時間に比例した値」へ変える。DELAY_RECOVERY_BOOST は 1.0 に戻して検証してから調整するのが安全です。この所見は仮説であり、実測で検証してから手を入れてください。
