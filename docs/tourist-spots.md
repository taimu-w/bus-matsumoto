# 観光スポット情報機能

## 概要

バス停付近の観光スポット情報を写真付きで表示し、経路検索でも観光スポット名（かな・ローマ字含む）で出発地・目的地を指定できるようにする。

## 背景・方針

- 観光スポット情報はGTFS由来のデータ（バス停・時刻表）とは完全に独立させる。GTFSフィード更新のたびに`stop_id`や統合バス停キーが入れ替わりうるため、観光スポット側から特定のバス停IDへ直接紐付けると更新時にリンク切れ・誤紐付けが起こる。
- バス停との関連付けは**保存時ではなく参照時**に、緯度経度による近接検索（ハバーサイン距離、`utils/geo.js`を流用）で都度解決する。これにより「全乗り場ページ」でも「乗り場別ページ」でも、同じロジックで自然に表示できる（乗り場ごとの追加設計は不要）。
- 写真の実体は自前サーバー/DBに置かず、Cloudinaryに**手動でアップロード**し、発行されたURLのみをDBに保存する。Render環境はコンテナのファイルシステムが再デプロイのたびに初期化されるため、ローカルディスク保存は不採用。
- 観光スポットの登録・編集は管理画面（`admin.html`、Basic認証で保護済み）にセクションを追加し、**テキスト一括入力（タブ区切り、全件洗い替え）**で行う。個別フォームは作らない。
- 観光スポットの識別子は、テキスト一括入力の**1列目で管理者が指定するID**（`tourist_spots.id`、TEXT）。名称による名寄せはせず、IDが同じなら名称が変わっても同一スポットとして扱う。

## データモデル

### `tourist_spots` テーブル（新規）

| カラム | 型 | 説明 |
|---|---|---|
| `id` | text PK | 観光スポットの識別子。管理画面のテキスト一括入力の1列目で管理者が指定する（空欄不可・重複不可・64文字以内、「/」やタブ・改行などの制御文字は不可）。名称が変わっても`id`が同じなら同一スポット |
| `name` | text | 名称（変更可能。`id`が違えば同名の別スポットも登録できる） |
| `kana` | text | かな |
| `romaji` | text | ローマ字。未入力の場合は`utils/kana.js`のヘボン式変換ロジックを流用してサーバー側で自動生成する（バス停の`translations.txt`欠落時と同じ扱い） |
| `lat` | numeric | 緯度 |
| `lng` | numeric | 経度 |
| `url` | text | 観光スポットの参考/公式URL |
| `hours` | text | 営業時間（フリーテキスト。例：「9:00〜17:00（月曜休）」） |
| `stay_duration` | text | 滞在時間目安（フリーテキスト。例：「30分〜1時間」） |
| `description` | text | 説明文 |
| `hours_en` | text | 営業時間（英語版、フリーテキスト） |
| `stay_duration_en` | text | 滞在時間目安（英語版、フリーテキスト） |
| `description_en` | text | 説明文（英語版） |
| `photo_urls` | text | Cloudinary上の画像URL（手動アップロード後にコピー&ペースト）。複数枚は「,」区切りで連結して保持する。利用者画面では1枚ずつ表示するカルーセルで見せる（先頭の写真から開始） |
| `category` | text | カテゴリ（フリーテキスト。例：「神社」「公園」「グルメ」）。現時点では情報として保持するのみで、検索・表示の絞り込みには使わない |
| `display_tag` | text | 表示タグ。空欄、または「観光」「観光スポット」を含まない値のときは、バス停ページの周辺観光スポット表示（`findNearbySpots`）からのみ除外する（詳細は「表示：バス停ページ」参照） |

写真は1スポットにつき複数枚登録できる（`photo_urls` に「,」区切りで連結）。利用者画面での表示は「写真表示」節を参照。営業時間・滞在時間目安は構造化せずフリーテキストとする（手入力運用のため）。

英語版の3項目（`hours_en`/`stay_duration_en`/`description_en`）は、将来的な英語表示対応に備えて**登録欄のみ**を先行して用意するもの。現時点では利用者画面・経路検索結果ポップアップともに英語表示には未対応で、これらの値はDBに保存されるだけで画面には出さない。名称・かな・ローマ字・URL・写真URLは言語非依存のため英語版を別途持たない。

`display_tag`（表示）は、経路検索の出発地・目的地としては使いたいが観光スポットではない地点（学校・病院など）が誤って観光スポットとして掲載されてしまうことへの対策。**バス停ページの周辺観光スポット表示にだけ**効き、地点名での経路検索（`searchTouristSpots`）・経路検索結果のスポット詳細ポップアップ（`GET /api/tourist-spots/:id`）は`display_tag`の値に関わらず従来どおり動作する。`category`（カテゴリ）とは独立した項目であり、カテゴリ名で「観光」と入力しても表示扱いにはならない（`display_tag`側に「観光」または「観光スポット」を入力する必要がある）。

### 既存テーブルとの関係

観光スポットとバス停・停留所を結ぶ外部キーは持たない。表示・検索時に都度、緯度経度で近接判定する。

## 管理画面（admin.html）

- 「観光スポット管理」セクションを追加（既存のお知らせ編集などと同じ並び）
- `<textarea>` 1個＋「登録」ボタンのみのシンプルなUI
- 入力フォーマット：1行1件、**タブ区切り**（スプレッドシートからのコピペを想定。カンマ区切りは説明文中の読点以外の記号と衝突する可能性があるため不採用）

  ```
  ID	名称	かな	ローマ字	緯度	経度	URL	営業時間	滞在時間目安	説明	営業時間（英語）	滞在時間目安（英語）	説明（英語）	写真URL	カテゴリ	表示
  matsumotojo	松本城	まつもとじょう	Matsumoto-jo	36.2381	137.9686	https://...	8:30〜17:00	1時間程度	国宝五重六階の天守	8:30-17:00	About 1 hour	A castle with a five-story, six-floor keep designated as a national treasure	https://res.cloudinary.com/.../a.jpg,https://res.cloudinary.com/.../b.jpg	史跡	観光
  ```

  未入力の項目があっても登録できるようにしてください。
  未入力の項目は利用者画面に表示しないでください。
  観光スポットのURLの表示はURLをそのまま配置せずに工夫してください。
  写真URL列は「,」（カンマ）区切りで複数枚指定できる。各要素が`https://`始まりかを検証し、前後空白・空要素を落として連結保存する。

- ローマ字列が空の場合はサーバー側で自動生成する
- 一覧表示（サムネイル＋ID＋名称）と、行単位の削除は別途簡易UIで用意する

### 登録ロジック（全件洗い替え／UPSERT）

- テキストを行ごとに分割し、タブでパースしてバリデーション（IDが空欄でない・重複していない・使用可能な文字か、緯度経度が数値か、URLが`https://`で始まるか等）
- 1件でもエラーがあれば**全体を保存せず**、エラー行と理由を返す（部分的な登録による不整合を避ける）
- 保存は1列目のIDをキーにしたUPSERT（同じIDなら更新、なければ新規作成、テキストに存在しないIDの既存行は削除）。名称もUPSERTの更新対象に含める（IDが同じなら名称の変更は同一スポットの改称として反映する）
- 運用上のマスターはスプレッドシート側に置き、追記・修正のたびに全内容をテキストエリアに貼り直す想定
- 掲載をやめるときはテキストから該当行を外す（＝全件洗い替えで削除される）。一時的に隠すためのフラグは持たない

## 表示：バス停ページ

- 「全乗り場ページ」「乗り場別ページ」の両方で、そのページが持つ座標を基準に近接検索APIを呼び出す
- 表示条件：半径500m以内・距離が近い順に最大5件（バス停統合しきい値400mを参考にした初期値。運用を見て調整）
- 各スポットに最寄りバス停までの距離・徒歩分数の概算を併記する。距離（`distanceMeters`）は直線距離（ハバーサイン）だが、徒歩分数（`walkMinutes`）は `utils/geo.js` の `estimateWalkMinutes()` で、直線距離に迂回係数・信号待ちを織り込んで換算する（距離が伸びるほど大きくなる）
- 写真はカード上部にカルーセルで出す（「写真表示」節）
- 公式サイトリンクのタップは `POST /api/tourist-spots/:id/link-click` へ記録する（下記「リンクのアクセス数（タップ回数）の計測」）
- `display_tag`（表示）が空欄、または「観光」「観光スポット」を含まない値のスポットは表示対象から除外する（経路検索の地点としては使うが観光スポットではない登録＝学校・病院等への対策）

### API：`GET /api/busstop/:stopKey/nearby-spots`

対象バス停の緯度経度を取得し、`tourist_spots`（`display_tag`が「観光」を含むもののみ）とのハバーサイン距離を計算して、半径内・上位N件を距離順に返す。

## 経路検索：地点名検索

- 出発地・目的地の入力候補に、既存のバス停名候補と観光スポット名候補（名称・かな・ローマ字の部分一致）を混ぜて出す（`display_tag`の値に関わらず観光スポットは全件が候補になる。バス停ページの周辺観光スポット表示だけを絞る項目であり、経路検索の地点としての利用は妨げない）
- 観光スポットが選択された場合、その座標から半径内の全バス停を解決し、**それぞれを起点/終点として経路検索を実行して結果をマージ**する
  - マージ後は「便ID＋乗車バス停」で重複除去し、所要時間順に並べ直す
  - 検索半径は表示半径と揃えて500m程度、対象バス停数の上限も数件に絞り、既存の経路検索（RAPTOR型、乗換2回まで）への負荷が半径内バス停数倍に膨らまないようにする
- 半径内にバス停が1件も見つからない場合は、既存の「0件時に条件を段階的に緩める」フォールバック方針を踏襲し、「見つかりませんでした」だけを返さない

## 経路検索：結果画面でのスポット詳細ポップアップ

- 出発地/目的地に観光スポットを指定して検索したとき、結果ヘッダーのスポット名（`viaSpotFrom.name`/`viaSpotTo.name`）をタップすると、写真（カルーセル。「写真表示」節）・営業時間・滞在時間目安・説明文・URLを表示するポップアップを開く。公式サイトリンクのタップは `POST /api/tourist-spots/:id/link-click` へ記録する
- ポップアップは`index.html`内の`rs-spot-modal`（既存の`bs-map-modal`等と同じ`window.openModal`/`closeModal`方式）を使い回す
- 詳細取得は`GET /api/tourist-spots/:id`（`display_tag`の値は問わない、公開API）。経路検索結果の`viaSpotFrom`/`viaSpotTo`は`spotId`・`name`・徒歩情報しか持たないため、タップ時に都度この単発取得APIを呼ぶ
- 取得に失敗してもポップアップ内にエラー文言を出すだけに留める（soft-fail。経路検索結果自体の表示は妨げない）

## 写真表示（カルーセル）

バス停ページの周辺観光スポット・経路検索のスポット詳細ポップアップ・スポット検索のスポット情報カードは、いずれも写真表示を共通モジュール `frontend/spot-photos.js`（`window.SpotPhotos`）に一本化する。各画面は `SpotPhotos.markup(spot, opts)` でHTMLを組み立て、DOMへ挿入したあとに `SpotPhotos.hydrate(scope)` を呼ぶだけ（`busstop.js`・`routesearch.js`・`spotsearch.js` より前に読み込む）。`opts.height` でスライドの高さ、`opts.wrapClass` でルート要素の角丸・余白を渡す。

- **1回に表示するのは1枚だけ。** `photoUrls` が2枚以上のときは横1枚ずつのカルーセルにする。
- **自動送りは複数枚のときだけ、5秒間隔。** タブが非アクティブ（`document.hidden`）・カルーセルが画面外（IntersectionObserver）・操作中（ポインタ押下中／ホバー中／キーボードフォーカス中）は停止する。手動操作の直後は次の自動送りまで5秒を置き直す。
- **手動切り替えはスワイプ・左右の矢印ボタン・下部インジケーターの3通り。** スワイプは指を離した時点の移動量で判定する（ドラッグ追従はしない）。横スワイプはJSで拾い、縦スクロールはブラウザに任せる（`touch-action: pan-y`）。
- **`prefers-reduced-motion: reduce` のときは自動送りしない**（手動操作は可能）。
- **写真が1枚だけのときは操作要素を出さず、全幅の静止画。** 写真ゼロなら空文字（カード側で写真領域ごと出さない）。
- 自動送りは1本の共有 `setInterval` とレジストリで回し、各tickで `root.isConnected` を見てDOMから外れたカルーセルを登録解除する（画面の再描画でタイマーが漏れ残らないため）。CSSは `frontend/style.css` の `.spot-carousel*`。

## 写真アップロード運用フロー

1. Cloudinaryアカウント（無料枠）にログインし、管理画面から画像を手動アップロード
2. 発行された配信URL（`secure_url`）をコピー
3. admin.htmlのテキスト一括入力の該当行の`写真URL`列に貼り付けて登録（複数枚は「,」区切りで並べる。カルーセルは先頭の写真から開始する）

アプリ側にはCloudinaryへのアップロードAPI連携（multer等）は実装しない。DBには画像URLの文字列のみを保持し、表示は`<img src>`でCloudinaryから直接配信する。

再登録（全件洗い替え）を何度行ってもCloudinary側へのリクエストは発生しないため、無料枠（ストレージ・配信帯域）への影響はない。ストレージは実際に新規アップロードした画像の分だけ、配信帯域は利用者が実際に写真を閲覧した回数分だけ消費される。

## リンクのアクセス数（タップ回数）の計測

観光スポットの公式サイトリンク（`tourist_spots.url`）が利用者にどれだけタップされているかを集計し、「その観光スポットを掲載する価値があるか」を管理者が判断できるようにする。

### データモデル：`tourist_spot_link_clicks` テーブル（新規）

| カラム | 型 | 説明 |
|---|---|---|
| `spot_id` | text | 対象スポットの `tourist_spots.id`（管理画面で指定する識別子）。**外部キーは張らない**（下記の理由） |
| `spot_name` | text | 記録時点の名称スナップショット。全件洗い替えでスポット行が消えても集計を残し、掲載終了スポットを名前で表示するため |
| `click_date` | date | Asia/Tokyo基準の日付。日別にカウントする |
| `click_count` | integer | その日のタップ回数 |
| `updated_at` | timestamptz | 最終更新 |

主キー `(spot_id, click_date)`。`click_date` に単独インデックス（期間集計の走査用）。

- **日別カウント**にしているのは、期間内の合計が分かれば用途を満たすため。生ログ（タップ1件＝1行）は持たない。
- **外部キーを張らない**のは、管理画面の運用が「テキスト一括入力・全件洗い替え（IDキーUPSERT＋テキストに無いIDはDELETE）」であり、テキストからIDの行を消してスポットを掲載終了しても、過去の集計を残したいため（`busstop_notices` がGTFSインデックスへ固い外部キーを張らないのと同じ方針）。IDが同じなら名称を変えても集計は同じ行に積み上がり、テキストからIDを消す／別のIDに付け替えたときだけ履歴が分かれる（消えた側は最後の名称スナップショットで `listed:false` として残る）。
- 保持は約400日（`services/touristSpots.js` の `LINK_CLICK_RETENTION_DAYS`。1年ルックバックが常に成立するよう13か月弱）。`scheduler.js` の1時間掃除から `purgeOldLinkClicks()` が古い行を削除する。

### 記録：`POST /api/tourist-spots/:id/link-click`（公開）

バス停ページ（`busstop.js`）と経路検索の詳細ポップアップ（`routesearch.js`）の「公式サイトを見る」リンクを、`navigator.sendBeacon` で叩く（未対応時は `fetch(..., {keepalive:true})`）。`<a target="_blank">` の遷移はそのまま。

- 本文もクライアントIDも取らない。結果に関わらず `{ ok: true }` を返す（掲載の有用性の目安なので、二重タップ等の厳密な重複排除はしない）。
- サーバー側は `services/touristSpots.js` の `recordLinkClick(spotId)` が、**URLが登録されているスポットだけ**を対象に当日行を +1 する（URL未登録・存在しないIDは静かに0件で終わる）。

### 集計：`GET /api/admin/tourist-spots/link-clicks?from=YYYY-MM-DD&to=YYYY-MM-DD`（管理）

管理画面のサイドバー「観光スポットのアクセス数」（`section-tourist-spot-clicks` / `admin-tourist-spot-clicks.js`）から、期間を指定して集計する。

- 期間は**最大1年（366日）**。未指定なら直近30日。`from > to` や366日超は400。
- `services/touristSpots.js` の `getLinkClickStats()` が、期間内のタップ数をスポットごとに合計する。現在掲載中のスポットは0回でも行に含め（掲載したが使われていないスポットが分かる）、集計にしか残っていない（＝掲載終了した）スポットはスナップショット名で `listed:false` として返す。`clicks` 降順→名称昇順。
- 管理画面は名称／状態（掲載中・掲載終了）／タップ回数の表と合計を表示する。

## 補足

- `category`（カテゴリ）は列として保持するのみで、検索・表示の絞り込みには使っていない。
- 表示半径（500m）・最大表示件数（5件）・経路検索の対象バス停数上限は運用を見て調整する余地のある初期値。
- 観光スポットの個別ページ（`/spot/{id}`のような直リンク）は無い。
